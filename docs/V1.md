# AI Loop Kit v1: how it works

This is the one description of the kit. If the code and this file disagree,
the code is the truth and this file has a bug.

## The kit in one sentence

A state machine whose every state is a loop, where agents do the work,
scripts decide, and the person approves the contract and the merge.

## The five principles

1. **Agents produce, scripts decide, the person approves.** No agent says a
   piece is done. The gate runs the checks itself.
2. **A piece is a contract.** Nothing is built without the person's intent and
   a judge that fails on today's `main`.
3. **Every state is a loop.** Each has an entry check, a work loop, an exit
   check and a way back. A piece that fails goes back with a typed reason,
   never forward.
4. **Hold rules in code, and label what is only words.** Every promise in this
   file names what holds it: the gate, a hook, or words.
5. **Grow from evidence.** After v1, a new judge kind, role or check joins
   only when a run shows the need. The failure goes in `docs/LEDGER.md` first.

## The four parts

### 1. The engine: states with gates

A piece is a GitHub issue with one state label. Only `gate.py` moves it.

```text
          capture         ready (checks)       claim
  idea ─────────► shaping ─────────────► ready ─────► building
                    ▲  ▲                   │             │
                    │  └──── pull-back ────┘             │ submit (gate judges)
                    │                                    ▼
                    ├──────── give-back ◄──────────── approval ──merged──► done
                    └──────── reject ◄────────────────┘
  drop: shaping, ready, building or approval ──► dropped ──reopen──► shaping
```

| Move | From, to | Started by | The gate checks |
| --- | --- | --- | --- |
| capture | new, shaping | shape skill | nothing |
| ready | shaping, ready | shape skill | the contract checks and the judge checks below |
| pull-back | ready, shaping | person or agent | a typed reason |
| claim | ready, building | `run.py` | spec and bar unchanged; the pushed branch has nothing local lacks |
| submit | building, approval | `run.py` | the judge, `Keep:`, the quality checks and the bar, all run by the gate |
| give-back | building, shaping | `run.py` | a typed reason; adds `needs-you` |
| merged | approval, done | `gate.py sync` | the pull request is merged |
| reject | approval, shaping | person's words | a typed reason; adds `needs-you` |
| drop, reopen | to and from dropped | person | a reason |

**Typed reasons.** Every move back carries one type: `spec-unclear`,
`bar-wrong`, `stopped`, `environment`, `builder-failed`, `person-rejected`,
`conflict` or `judge-gap`, plus free text. `gate.py report` counts them across
pieces. This is the seed of the meta loop: the kit observes where pieces
fail, and the person decides what to change.

**One run at a time.** A run takes a lock in `.loop/run.lock`. At start it
returns any piece left in building by a dead run to shaping, with the type
`environment`. `gate.py stop` asks a running run to stop after the current
attempt.

Before each piece, the run checks the approval queue. When it reaches the
`Waiting limit:` (default 3), the run prints one `next:` step and starts no
new piece until a pull request is reviewed or merged.

### 2. The contract: two parts

The issue body has two parts. The person approves both before ready.

```markdown
## Intent
What the person wants and why, in their words.

Out of scope:
- What this piece does not do.

## Approach
Optional. The path for the builder: the files or modules to change, the
public interface to add, tools to use, constraints. Say how, not only what.

## Contract
- D1: When I run `tally --top 2 words.txt`, then it prints `b 3` then `a 2`.
- D2 (stays): Without `--top`, the output is unchanged.

## Judge
Kind: feature
Command: `python -m pytest tests/judge/test_piece_top.py -q`
Files:
- tests/judge/test_piece_top.py
Keep: `python -m pytest`
```

- **Intent** holds what code cannot say: the why and the limits. The gate
  refuses an empty Intent or an empty `Out of scope` list.
- **Contract** items are numbered and concrete, with an example in each. One
  test per item, with the ID in the test name.
- **Judge** is the machine's copy of the contract. It is written by a
  separate judge writer (see Roles), fails on `main`, and is fixed by a hash.
- **After the merge the issue is a closed record.** The tests are the living
  spec. Each judge file starts with a comment that gives the intent in one
  line. Nobody edits a closed issue to keep it current.

### 3. Loop mechanisms: one loop, the judge kind changes

The build loop is always the same: a fresh attempt, the gate judges, then
retry or hand back. The `Kind:` line chooses what the judge is.

| Kind | Judge | Fails on main? | In v1 |
| --- | --- | --- | --- |
| feature | acceptance tests for new behaviour | yes | yes |
| fix | a test that reproduces the bug | yes | yes |
| scaffold | the test runner runs and passes | no (skipped, and the record says so) | yes |
| goal | a measurement with a threshold | yes | later |
| gauntlet | a blind critic against a reference | not applicable | later |

A `fix` piece's Intent says what happens now and what should happen. Its
first Contract item is the bug, as a "When ..., then ..." sentence.

At submit, the gate also refuses unapproved growth from fewer than 1,000
lines to 1,000 or more in a file. `Large file: <path>` in the Judge section
allows a named file. The pull request lists any file above that size. Python
projects may run `quality/crap.py` on changed functions using the project's
coverage.py JSON and `git diff -U0`; it fails above CRAP 30. The kit does not
run coverage itself. Node setup offers ESLint complexity only.

Before each build, the brief lists project files importing modules or files
named in Approach. The run pauses before starting another piece when the
approval queue reaches its `Waiting limit:` (default 3), with a `next:` step.

### 4. Roles: agents produce, scripts decide

| Role | What it is | Sees | Produces |
| --- | --- | --- | --- |
| Shaper | the shape skill, with the person | the code, the person | Intent, Approach, Contract |
| Judge writer | a fresh subagent | the contract and the code, not the shaper's notes | the judge files |
| Builder | a fresh `claude -p` per attempt | the contract, the judge, the last failure | code on the piece branch |
| Standards reviewer | a fresh `claude -p` after the gate passes | the diff and project standards, or the built-in heuristics | checked local fixes, follow-up pieces, or nothing |
| Contract reviewer | another fresh `claude -p` | Intent, Out of scope, Approach, Contract and the diff | judge-gap findings, or nothing |
| Gate | `gate.py`, a script | everything | every decision and record |
| Run | `run.py`, a script | the ready pieces | attempts, reviews, pull requests |
| Person | you | the contract, the pull request | the approval and the merge |

- The shaper never writes the judge, and the builder never sees the shaper's
  conversation. Each agent grades nobody's work but its own output.
- Coding standards live in the project's standards file (named in the loop
  section of `AGENTS.md`), read only by the reviewer. They are not in the
  builder's brief and not in `AGENTS.md`, so the builder's context stays
  small.
- After the reviewer commits, the gate runs every check again. If a check
  fails, the reviewer's commits are dropped and the builder's judged commit
  goes forward.
- The judge writer and both reviewers end with a tagged JSON verdict. The
  run uses the last tagged block. Missing, malformed or wrongly shaped JSON
  returns the piece to shaping with an `environment` reason and keeps the raw
  output tail in the log.
- Test guidance asks what production change should fail each test, uses
  literal expected values, and avoids source-text checks unless the Contract
  names the file. The ready lint also rejects same-function comparisons and
  source-file reads.

Judges use only a module's caller interface. If a judge needs internals, the
reviewers report a follow-up piece for the module's shape. The standards
review checks whether abstractions remove complexity, seams have two real
adapters, and tests for removed modules are replaced.

Builder and reviewer attempts stop after ten minutes without output by
default. `Idle limit:` changes that number of minutes. The 40-minute hard
limit remains. Idle attempts return with `builder-failed` and `idle` in the
reason. A dirty build folder returns with an `environment` reason and a
`next:` step; the run never resets or cleans it.

## What the gate checks

### At ready

| Check | Held by |
| --- | --- |
| Intent, `Out of scope` and Contract are present; each item has an ID | gate |
| The judge fails on `main` on an assertion, and every non-`(stays)` ID is on a failing line | gate |
| `(stays)` items hold on `main` | gate |
| `Keep:` and Prepare pass on a fresh `main` (Prepare is skipped for scaffold) | gate |
| The judge has no test without an assertion, no `assert True` or `x == x`, no skip, `xfail`, `.only` or `.skip` | gate (`testlint.py`) |
| A judge does not import private project names or inspect source text unless the Contract names that check | gate (`testlint.py`) |
| The spec and the bar are hashed. The bar is the judge files plus every `conftest.py` and test helper they rely on | gate |

### At submit, after each attempt and after the review

| Check | Held by |
| --- | --- |
| The bar is unchanged; a changed judge is put back and the attempt fails | gate |
| No existing test file, `conftest.py` or fixture changed unless the Contract names it | gate |
| No check setting changed (lint, test, CI config, `.gitignore`, check keys) unless `Settings: may change` | gate |
| No file added under paths Prepare created | gate |
| No file changed under a protected path unless the Contract names it | gate |
| No conflict markers | gate |
| The judge passes, `Keep:` passes, with nothing skipped | gate |
| Each `Quality:` command in `AGENTS.md` passes (for example mutation testing or a complexity limit) | gate |
| No secret shape in the diff | gate |

**Quality commands** are the project's own, not the kit's, so the kit stays
small and works for any stack. Setup offers CRAP from coverage.py JSON for
Python and ESLint's `complexity` rule for Node. Mutation testing is
experimental. Setup checks that mutmut 3.8 or later is installed and that
`source_paths` is configured. Mutmut scores code called in the same Python
process. When acceptance tests launch a separate process, setup recommends
keeping them in Test and selecting a focused in-process adapter test for
mutmut. Node CRAP waits.
Doctor runs the Test command before each Quality command in the same fresh copy
of main, so coverage-based checks can read the coverage file Test creates. For
a proposed Quality command, doctor first applies that command to the fresh
copy's loop section, then runs Prepare, Test and Quality.

## The pull request, written for a person

The gate writes the facts. The builder writes only the why.

- **What changed:** files by area, tests added, new dependencies.
- **Risk:** protected paths, migrations, config, CI or check settings
  touched; how many files import the changed modules; how hard a revert is.
- **Evidence:** the judge output, the `Keep:` result, each quality result,
  the bar hash, the judged commit.
- **Why and what could go wrong:** two short paragraphs from the builder.
- **Review:** what the reviewer changed, if anything.

## The boundary

| Rule | Held by |
| --- | --- |
| No push to `main`, no force push, no agent merge, no recursive delete | the guard hook. It reads `git -C`, `git -c`, `gh -R`, `bash -c` and `sh -c` forms; in build sessions it refuses unreadable command forms |
| Builders and reviewers never push, never call `gh`, never edit `.claude/`, `.githooks/` or protected paths | the guard hook, in the build session |
| The gate is the only mover of state | the guard refuses label edits; `audit.py` finds any it missed |
| `main` refuses direct pushes on GitHub | branch protection, offered by setup where the plan allows it; `doctor` reports whether it is on |
| No secret in a tracked file | the gate's secret check at submit, and words |
| The spec says what the person meant | words: the person approves the contract |

The guard is a seatbelt, not a sandbox. Runs are attended. A sandbox comes
before any run is left alone.

## A day with the kit

1. `/plugin marketplace add gwpicard/ai-loop-kit`, then
   `/plugin install ai-loop-kit@ai-loop-kit`.
2. `/ai-loop-kit:setup`: labels, the Prepare, Test and Quality commands, the
   standards file and protected paths. You approve and merge its pull
   request. Doctor checks it all on a fresh copy of `main`.
3. `/ai-loop-kit:shape <idea>`: questions, the split, the Intent and
   Contract. You approve. The judge writer writes the judge; the gate marks it
   ready.
4. `/ai-loop-kit:run`: builds every ready piece. Each passing piece gets a
   review and a pull request.
5. You read the pull request and merge it, or reject it with a reason.
   `gate.py sync` moves merged pieces to done.
6. `gate.py report` shows where pieces came back and why.

## Later, and why

| Later | Why it waits |
| --- | --- |
| goal and gauntlet kinds | they need a measurement harness and a critic |
| researcher role | no run has needed one yet |
| integration branch, combined review | the person reviews each pull request for now |
| sandbox, walk-away runs, notifications | the boundary must be strong first |
| GitHub App identity | the person's `gh` sign-in is enough while runs are attended |
| maintenance and live feedback loops | they need projects that live for weeks |
| explain-back, structure diagrams | wait for a run that shows rubber-stamp merges |

## Size

The kit has 3,439 tracked Python lines in `kit/`; its target is about 2,500.
It uses the standard library only and supports Python 3.9 or later.
