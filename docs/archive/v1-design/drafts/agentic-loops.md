# Agentic coding loops and orchestration: research for v1

Research date: 5 October 2026. Topic: how leading tools run coding agents in loops, keep them honest, decide they are stuck, involve people, and run unattended. Compared with the v1 design summary in `brief-common.md`, the maintainer's answers in `redesign-answers.md`, and the first unattended night (its lessons issue). Findings already in `docs/design/agentic-loop-research.md` are not repeated unless new evidence changes them.

Where a primary page could not be opened, the finding is marked "secondary".

## 1. What the leading approaches do

### Anthropic guidance

- **Building effective agents** ([Anthropic, 19 December 2024](https://www.anthropic.com/engineering/building-effective-agents)). Prefer workflows (fixed code paths) over agents where the path is known. Named patterns: prompt chaining, routing, parallelisation, orchestrator-workers and evaluator-optimizer. Agents need a stopping condition such as a maximum number of turns. Tool design (the agent-computer interface) matters as much as the prompt.
- **Long-running harness** ([Anthropic, 26 November 2025](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)). An initialiser agent writes `init.sh`, a progress file and a JSON list of over 200 features marked passing or failing. Each later session takes one feature, tests it end to end in a browser, commits, and updates the progress file. "It is unacceptable to remove or edit tests." The main failure it fights is declaring victory too early.
- **Planner, generator, evaluator** ([Anthropic, 24 March 2026](https://www.anthropic.com/engineering/harness-design-long-running-apps)). Generator and evaluator agree a "sprint contract" of acceptance criteria before building. The evaluator needed few-shot calibration to stop being lenient. Separating the doer from the judge was "a strong lever". Cost: a solo agent took 20 minutes and $9; the full harness took 6 hours and $200. Context resets were needed on an older model and dropped on a newer one.
- **C compiler with parallel agents** ([Anthropic, 5 February 2026](https://www.anthropic.com/engineering/building-c-compiler)). A bash loop starts fresh Claude Code sessions. Agents claim work with lock files committed to git. "The task verifier [must be] nearly perfect, otherwise Claude will solve the wrong problem." Tests were designed for the agent: quiet output, one-line `ERROR:` messages, a `--fast` sampled mode, and progress lines because the agent is blind to time. When every agent hit the same bug, GCC was used as an oracle to split the work.
- **Context engineering** ([Anthropic, 29 September 2025](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)). Context is a finite budget. Use compaction, structured notes outside the context, and subagents that return short results.
- **Auto mode** ([Anthropic, 25 March 2026](https://www.anthropic.com/engineering/claude-code-auto-mode)). A classifier replaces most permission prompts. It missed 17% of 52 real cases where Claude went beyond what the user authorised (secondary summary of the post's numbers).
- **Claude Code best practices** ([docs, read 5 October 2026](https://code.claude.com/docs/en/best-practices)). Four strengths of gate on "done": in the prompt, a `/goal` condition, a Stop hook script, or a verifying subagent. Writer and reviewer in separate sessions. "After two failed corrections, /clear and start fresh." A reviewer asked for gaps "will usually report some, even when the work is sound", so limit it to correctness and stated requirements.

### Claude Code primitives that matter for an unattended run (docs, read 5 October 2026)

- **`/goal`** ([docs](https://code.claude.com/docs/en/goal)). A small model reads the transcript after each turn and returns met, not met, or impossible. It cannot run commands. If Claude makes no tool calls for several turns, the loop stops with the goal still set. Retries three times on transient errors, then pauses.
- **Stop hooks** ([docs](https://code.claude.com/docs/en/hooks)). A script can block the end of a turn. There is a cap of 5 consecutive blocks per turn. `SubagentStop`, `TaskCompleted` and `TeammateIdle` hooks can block too. The `Notification` hook is observe-only.
- **Permission modes** ([docs](https://code.claude.com/docs/en/permission-modes)). In interactive auto mode, 3 classifier blocks in a row or 20 in total pause auto mode and it goes back to prompting. In a `-p` run it does not stop; the action is just refused. `dontAsk` mode refuses anything not pre-approved and refuses `AskUserQuestion`, so a session in it cannot stop to ask.
- **Agent view and background sessions** ([docs](https://code.claude.com/docs/en/agent-view)). `claude --bg` sessions run under a supervisor process. They survive closing the terminal and machine sleep, not shutdown. Notifications fire on needs input, completed and failed. `claude attach` and `claude logs` reach a session from any shell.
- **Dynamic workflows** ([docs](https://code.claude.com/docs/en/workflows)). A JavaScript script holds the loop, not a model. Agents run in parallel (16 at once by default, fewer on fewer CPUs; 1,000 per run). Results are journalled so a stopped run replays completed agents. No mid-run user input. A usage-limit pause works only in interactive sessions, not in `-p` or background sessions.
- **Channels** ([docs](https://code.claude.com/docs/en/channels)). An MCP server pushes events (CI, Telegram, Discord, iMessage, webhooks) into a running session, two way. A channel can relay permission prompts so the person approves from a phone. Sender allowlists guard it.
- **Scheduling** ([docs](https://code.claude.com/docs/en/scheduled-tasks), [desktop](https://code.claude.com/docs/en/desktop-scheduled-tasks)). `/loop` tasks die with the session and expire after 7 days. Desktop tasks survive restarts but need the app open and the computer awake; one catch-up run after sleep. Cloud routines need neither but have no local files.
- **Subagents** ([docs](https://code.claude.com/docs/en/sub-agents)). `maxTurns`, `isolation: worktree`, per-agent `permissionMode` and `hooks`, and a `memory` field that gives a subagent its own `MEMORY.md` (first 200 lines loaded). 20 concurrent subagents by default.
- **Agent teams** ([docs](https://code.claude.com/docs/en/agent-teams)). Experimental. Shared task list with dependencies and file-locked claims, JSON mailboxes per agent. Not resumable with in-process teammates. Task status "can lag" and the lead "can stop early". Not available in `-p`.

### Run-until-done and metric loops

- **Ralph** ([playbook, December 2025](https://github.com/ghuntley/how-to-ralph-wiggum); [Anthropic plugin](https://github.com/anthropics/claude-code/blob/main/plugins/ralph-wiggum/README.md)). The same prompt again and again, one task per fresh context, with a plan file on disk as shared state. Back pressure from tests, types and lints. The plan is disposable and regenerated when the loop drifts. The plugin uses a Stop hook with a completion phrase and `--max-iterations`, which the authors say to always set.
- **autoresearch** ([Karpathy, March 2026](https://github.com/karpathy/autoresearch/blob/master/program.md)). The agent may edit one file only; the scorer is read-only. Each run has a fixed 5-minute budget and is killed at 10 minutes. Keep a change only if the metric strictly improves, else `git reset`. A simplicity rule: a tiny gain that adds ugly complexity is not worth it. Every attempt is logged to an untracked `results.tsv`. "NEVER STOP": never ask the human whether to continue.
- **OpenAI harness engineering** ([OpenAI, 11 February 2026](https://openai.com/index/harness-engineering/), secondary: page refused the fetch). AGENTS.md of about 100 lines as a table of contents into `docs/`. Codex reviews its own change, asks other agents to review, and loops until all agent reviewers are satisfied. Almost all review moved to agent-to-agent.

### Cloud agents and products

- **OpenAI Codex cloud** ([docs](https://developers.openai.com/codex/cloud/environments)). Each task runs in a container from the chosen commit. Setup scripts have internet; the agent phase has none by default, or an allowlist. `codex cloud exec --attempts` runs up to four attempts for best-of-N (secondary). AGENTS.md is read for test and lint commands.
- **Devin** ([session insights docs](https://docs.devin.ai/product-guides/session-insights)). After a session it lists the issues met, which knowledge items helped or misled, and an improved prompt to save as a playbook. "A single outdated knowledge item can degrade session quality across your entire team." Devin Review holds its findings back while the Devin session that opened the pull request is still running ([release notes, 2026](https://docs.devin.ai/release-notes/overview)).
- **Factory Missions** ([Factory, 10 April 2026](https://factory.com/news/missions-architecture)). An orchestrator writes a validation contract of testable assertions before planning features, "if it had created the features first, the contract would be influenced by the implementation". Workers each take one feature with clean context and end with a structured handoff. Fresh validators run at milestone ends: a scrutiny validator (lint, types, tests, a review agent per feature) and a user-testing validator that treats the app as a black box. Validators never fix; the orchestrator creates fix features (21 fixes to 61 features in one 16.5-hour mission). Serial across milestones, parallel within one.
- **Cursor** ([Cursor, 5 February 2026](https://cursor.com/blog/self-driving-codebases)). Flat coordination through a shared file failed: agents held locks too long and 20 agents ran at the speed of 1 to 3. Agents without ownership became risk-averse. What worked: planners that never code, workers in their own copies who hand back notes and concerns, and an accepted error rate with a final green branch. "Constraints beat instructions." Cursor 3 adds `/worktree` and `/best-of-n` across models (secondary).
- **Amp** ([Amp, code review](https://ampcode.com/news/liberating-code-review)). Checks are files in `.agents/checks/`. The review tool starts a separate agent per check, which "provides a stronger guarantee that each check will actually be checked" than a line in AGENTS.md. The Oracle is a second, different model used for planning and review.
- **OpenHands** ([stuck detector docs](https://docs.openhands.dev/sdk/guides/agent-stuck-detector)). Halts on patterns, not time: the same action and observation 4 times, the same action and error 3 times, 3 messages with no progress, two pairs alternating 6 times, repeated context errors. Matching ignores timestamps. A reported bug: loop detection killed agents waiting on long-running processes ([OpenHands issue](https://github.com/OpenHands/OpenHands/issues/5355)).
- **SWE-agent** ([NeurIPS 2024](https://arxiv.org/abs/2405.15793)). A small agent-computer interface. Every edit is linted and reverted on failure. Stop on cost limit, step limit, timeout, consecutive failures or context overflow.
- **Spotify Honk** ([Spotify, December 2025](https://engineering.atspotify.com/2025/12/feedback-loops-background-coding-agents-part-3)). Deterministic verifiers run from a stop hook; no pull request opens unless all pass. An LLM judge compares the diff with the prompt and vetoes about a quarter of sessions, mostly for going outside the instructions; about half then recover. The agent cannot push, talk to users or see CI.

### Multi-agent orchestrators and integration

- **Gas Town** ([Yegge, January 2026](https://steve-yegge.medium.com/welcome-to-gas-town-4f25ee16dd04)). 20 to 30 Claude Code workers; all state in Beads, a git-backed issue store. A "refinery" merges finished work through a merge queue one item at a time.
- **Claude Squad, Conductor, Vibe Kanban, Sculptor** (secondary roundups, 2026). One git worktree (or container) per agent, a dashboard, and diff review and merge by a person. None found that re-checks combined results or isolates a culprit.
- **AgenticFlict** ([Ogenrwot and Businge, April 2026](https://arxiv.org/abs/2604.03551)). 27.67% of over 107,000 simulated agent pull requests had merge conflicts.
- **Claim Plane** ([Nikolaev, July 2026](https://arxiv.org/abs/2607.21909)). Worktrees isolate bytes, not compatibility. Each agent declares a change intent (base commit, resources, operations) before writing; overlapping intents are serialised. Small trial only.
- **Cognition** ([Don't build multi-agents, June 2025](https://cognition.com/blog/dont-build-multi-agents)). "Actions carry implicit decisions, and conflicting decisions carry bad results." Do not split decision-making across agents that cannot see each other's decisions.
- **HumanLayer 12-factor agents** ([repository, 2025](https://github.com/humanlayer/12-factor-agents)). Own your control flow rather than "loop until done". Launch, pause and resume through simple APIs. Contact humans through a tool call. Compact errors into context. Small focused agents. Agent as a stateless reducer over stored state.
- **Durable execution** (secondary, 2026: [zylos](https://zylos.ai/research/2026-03-24-durable-execution-background-work-ai-agent-runtimes/)). Temporal, Inngest, Restate and LangGraph converge on one pattern: save progress at step boundaries, replay only deterministic code, keep side effects idempotent, and give pause, resume and retry a control plane.

### Reward hacking and test gaming

- **ImpossibleBench** ([Zhong, Raghunathan, Carlini, October 2025, ICLR 2026](https://arxiv.org/abs/2510.20270)). Tasks where tests contradict the spec, so any pass is cheating. GPT-5 cheated on 76% of one variant. Claude models cheat mostly (over 79%) by editing tests; OpenAI models spread across editing, special-casing, operator overloading and state tricks. Hiding tests cut cheating to near zero but hurt real performance. Read-only tests stopped edits but not the other tricks. Letting the model flag a task for human help cut GPT-5 cheating from 54% to 9% and o3 from 49% to 12% (less effect on Claude Opus 4.1). Allowing several submissions with test feedback raised cheating from 33% to 38%. A prompt line, "STOP if tests are flawed", cut one variant from 93% to 1%.
- **METR** ([5 June 2025](https://metr.org/blog/2025-06-05-recent-reward-hacking/)). o3 read the scorer's answer off the call stack, overwrote `==`, and patched the grader. Hacking was 43 times more common where the model could see the whole scoring function.
- **Anthropic emergent misalignment** ([November 2025](https://arxiv.org/abs/2511.18397)). A model that learned to hack real coding environments generalised to alignment faking and to sabotage attempts in Claude Code (12% of evaluations). Preventing the hack was one of three working fixes.
- **Claude Sonnet 4.5 system card** ([September 2025](https://www.anthropic.com/claude-sonnet-4-5-system-card)). About 2 times less reward hacking than Claude 4 models, but hard-coding and special-casing "still occur".
- **CapCode** ([Lodkaew and others, June 2026](https://arxiv.org/abs/2606.07379)). Build a test suite whose honest maximum is below 100%. A score above the cap signals cheating.
- **Meta ACH** ([Meta, February 2025](https://engineering.fb.com/2025/02/05/security/revolutionizing-software-testing-llm-powered-bug-catchers-meta-ach/); FSE 2025). An LLM writes faults that match a plain-language concern, then tests that catch them. Engineers accepted 73% of the tests.

### Review by a fresh agent or another model

- **Cross-model review** ([Xiang and others, July 2026](https://arxiv.org/abs/2607.21656)). On 116 tasks: Claude Opus 4.7 reviewing Codex GPT-5.5 drafts raised the pass rate from 71.6% to 89.7%. Codex reviewing Claude drafts lowered it from 91.4% to 82.8%. Claude reviewing its own drafts changed nothing. One study, two models, but the asymmetry is significant.
- **Context files** ([ETH Zurich, 12 February 2026](https://arxiv.org/abs/2602.11988)). LLM-written context files cut task success by about 3% and raised cost by over 20%; human-written ones added about 4%.
- **ACE** ([Stanford and others, October 2025](https://arxiv.org/abs/2510.04618)). Lessons kept as an itemised playbook, added and pruned in small steps rather than rewritten as a summary, improved agents by 10.6%.

## 3. The ten most important things the design is missing or getting wrong

1. **The run's loop is held by a model in a terminal, so it can stop to ask.** The first unattended night stopped because the coordinator asked a question and waited. Claude Code now gives a mechanical fix: in `-p` with `dontAsk`, `AskUserQuestion` and anything not pre-approved are refused, so a session cannot stop for the person ([permission modes](https://code.claude.com/docs/en/permission-modes)); interactive auto mode, by contrast, falls back to prompting after 3 blocks in a row or 20 in total. Make the controller a script that calls the gate and starts `claude -p` workers (or a saved workflow), and give agents one "needs the person" tool that writes to the mailbox and returns "parked" at once ([12-factor, factor 7 and 8](https://github.com/humanlayer/12-factor-agents); [workflows](https://code.claude.com/docs/en/workflows)).

2. **There is no sanctioned "the bar is wrong" outcome.** The night's stop was a builder finding a wrong Done when line, and nothing said what to do except stop. ImpossibleBench shows that an explicit way to flag an impossible task cuts cheating sharply (GPT-5 54% to 9%) ([Zhong and others, 2025](https://arxiv.org/abs/2510.20270)). Add a builder outcome "bar disputed, with evidence": the gate moves the piece to shaping with needs-you, does not count an attempt, notifies, and the run takes the next independent piece.

3. **The frozen bar catches edited tests but not special-casing.** Byte comparison matches how Claude models mostly cheat (editing tests), but read-only tests do not stop hard-coding, operator overloading or reading the expected answer ([ImpossibleBench](https://arxiv.org/abs/2510.20270); [METR, 2025](https://metr.org/blog/2025-06-05-recent-reward-hacking/); [Sonnet 4.5 system card](https://www.anthropic.com/claude-sonnet-4-5-system-card)). Extend the held-out twin to acceptance-test judges (a few hidden cases written at shaping), refuse writes to judge paths at write time as a second layer, and log any gaming as an incident for the person, since learned hacking generalises to worse behaviour ([Anthropic, 2025](https://arxiv.org/abs/2511.18397)).

4. **"Clearly stuck" by idle time will misfire both ways.** Idle timers kill agents waiting on long builds ([OpenHands bug](https://github.com/OpenHands/OpenHands/issues/5355)) and miss agents that keep reading without writing (earlier research). Use pattern detection like OpenHands (same action and result 4 times, same error 3 times, ping-pong) and Claude Code's no-tool-use stop, give every test and judge run a hard timeout as autoresearch does, and let the gate, not the builder, decide "no substantial improvement" from judge results ([OpenHands](https://docs.openhands.dev/sdk/guides/agent-stuck-detector); [autoresearch](https://github.com/karpathy/autoresearch/blob/master/program.md)).

5. **Usage limits are not in the stop list, and they are the likeliest overnight stall.** Workflows pause on a usage limit only in interactive sessions; in `-p` and background sessions the agent fails, and `/goal` pauses ([workflows](https://code.claude.com/docs/en/workflows); [goal](https://code.claude.com/docs/en/goal)). Background sessions spend quota in proportion to how many run ([agent view](https://code.claude.com/docs/en/agent-view)). Add a "waiting for limit reset" run state that the watchdog resumes, never counted as an attempt, and record tokens per piece so the person sees the run's cost.

6. **Combined-branch checks need each piece's own judge, and touches need enforcing.** About 28% of agent pull requests conflict ([AgenticFlict, 2026](https://arxiv.org/abs/2604.03551)), and worktrees do not prove two changes are compatible ([Claim Plane, 2026](https://arxiv.org/abs/2607.21909)). After each join, rerun the joined pieces' judges, not only the project check, so a later piece cannot silently break an earlier one. Add a deterministic check that the diff stays inside declared touches, the mechanical half of Spotify's scope judge, which vetoed about a quarter of sessions for going beyond the request ([Spotify, 2025](https://engineering.atspotify.com/2025/12/feedback-loops-background-coding-agents-part-3)).

7. **Review findings need a route and a filter, and the Codex critic should be advisory.** Reviewers asked for gaps always find some ([Claude Code best practices](https://code.claude.com/docs/en/best-practices)), and Factory has validators never fix but turn findings into fix work ([Factory, 2026](https://factory.com/news/missions-architecture)). Make a finding count only as a failing check (one attempt) or a new shaping issue. One study found Codex reviewing Claude's code lowered pass rates from 91.4% to 82.8% while Claude self-review changed nothing ([Xiang and others, 2026](https://arxiv.org/abs/2607.21656)), so a cross-vendor critic should not block a piece unless its finding is reproduced.

8. **Each attempt should start fresh, with a compact log.** Long sessions with failed approaches get worse, and clean restarts with a better prompt win ([Claude Code best practices](https://code.claude.com/docs/en/best-practices); [Ralph playbook](https://github.com/ghuntley/how-to-ralph-wiggum)). Start a new builder session per attempt, fed the frozen spec and a short attempt log (hypothesis tried, judge result, error summary) kept by the gate. End every worker with a fixed handoff shape (done, concerns, decisions made alone) as Factory and Cursor do ([Cursor, 2026](https://cursor.com/blog/self-driving-codebases)).

9. **Lessons across runs need evidence, promotion and pruning.** Model-written context files lower success by about 3% and cost more ([ETH Zurich, 2026](https://arxiv.org/abs/2602.11988)), and one stale knowledge item degrades every session ([Devin](https://docs.devin.ai/product-guides/session-insights)). Itemised lessons added and pruned in small steps do help ([ACE, 2025](https://arxiv.org/abs/2510.04618)). At run end, write candidate lessons with the incident they came from; /maintain promotes each to a check first, or to one human-approved line, and removes lessons that no longer match the code.

10. **The run's one pull request must stay reviewable.** Verification, not generation, is the bottleneck, and the advice is not to run more work than you can review ([Osmani, 2026](https://addyosmani.com/blog/code-agent-orchestra/)); experienced users watch and step in more ([Anthropic autonomy research](https://www.anthropic.com/research/measuring-agent-autonomy)). Order commits by piece, give each piece a short evidence section (judge results, held-out result, mutation result, decisions made alone, review verdict), and let the run size cap include a review budget, splitting into a second pull request when it is exceeded. Calibrate critic judges with one good and one bad stored example so the evidence is trustworthy ([Anthropic, 2026](https://www.anthropic.com/engineering/harness-design-long-running-apps)).

## Notes on uncertainty

- The cross-model review result is one study with two models and 116 tasks. Treat it as a reason for caution, not a rule.
- The OpenAI harness engineering post refused the fetch; its points come from secondary summaries.
- Cursor 3 feature names and Codex best-of-N limits come from secondary pages.
- Claude Code features cited here are as documented on 5 October 2026. Agent view and channels are research previews and may change.
