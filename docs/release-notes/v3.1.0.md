# AI Loop Kit 3.1.0

This release makes a run lighter on the machine and easier to measure: merges run fewer full test suites, the loop runs at background priority, and `loop status` reports throughput and token use. It also adds issue kinds, a `loop check` command for sessions, a check that lists the paths an issue will touch while it is shaped, and fixes to the guard and the merge check.

Most changes apply to every project. One changes what a merge runs: in a project whose `Test files command` contains `{files}`, the loop now runs the full Test command only at every fourth merge and at the drain, and runs targeted tests at the merges in between. To restore a full run on every merge, set `"Full suite every": 1` in `loop.json`, as described under Updating. A project without such a `Test files command` still runs the full Test command at every merge.

## Updating

1. In Claude Code, refresh the marketplace, then update the plugin:

       /plugin marketplace update ai-loop-kit
       /plugin update ai-loop-kit@ai-loop-kit

2. Start a new Claude Code session so that the new plugin loads.
3. In the commands below, `<plugin>` is the installed plugin folder, the one that holds `bin/`. A loop that is already running keeps the version it started with. To move it to 3.1.0, stop it from the project root, wait until `.loop/loop.pid` is gone, and start it again:

       <plugin>/bin/loop stop
       mkdir -p .loop && nohup <plugin>/bin/loop run > .loop/loop.out 2>&1 &

This release needs no setup run. Settings, labels, parked issues, the loop branch and its pull requests carry over unchanged.

To keep the full Test command at every merge in a project with a `Test files command`, add this setting to `loop.json` before you restart:

    "Full suite every": 1

If you followed step 6 of the 3.0.0 notes and added `"loop.json"` and `"loop.local.json"` to your own `Protected paths` list, you can keep or remove those entries: both files at the repository root are now protected whatever the list holds.

## What changes

1. **The full suite runs every few merges, not at every merge.** A new optional `loop.json` setting, `Full suite every`, takes a whole number of at least one and defaults to 4. With the default and a `Test files command` that contains `{files}`, three merges in a row run the Test files command on the issue's locked tests and on the test modules that the branch changes against the loop branch, followed by the Check command; the fourth merge runs the full Test command. A value of 1 runs the full suite at every merge.

   Each merge records in `.loop/events.jsonl` whether the full suite ran, and the loop counts from that record, so the count survives a restart. A successful full run at merge, or a successful drain, starts the count again. A merge also runs the full suite when the issue has no posted list of locked test modules.

   If the full Test command fails at merge, the loop runs it once more on the head of the loop branch. When that run also fails, the issue parks with a note that the failure was already on the loop branch; otherwise the issue returns to its builder. The drain still runs the full suite before the end-of-loop pass and the final pull request. The trade-off: a regression outside the targeted tests can reach the loop branch and is found only at the next full run.
2. **The loop runs at background priority.** On macOS, `loop run` moves itself into the background class with `taskpolicy -b` before it starts any build, so the processes it starts inherit that class. On other systems it raises its nice value by 10. If either step fails, the loop writes `could not set background priority; continuing` to `loop.out` and carries on. On 21 November, when the class was set by hand on a running loop, the load average fell from about 11 to about 3. A build may take longer on an otherwise idle machine.
3. **Build temporary files live beside the worktrees.** Each build's temporary folder, which its commands and sessions inherit as `TMPDIR`, is now created in `.loop-worktrees`, in the folder that holds the project, instead of in the system temporary folder. On a Mac, the Spotlight exclusion that `kit/README.md` already advises for `.loop-worktrees` (System Settings, Spotlight, Search Privacy) now covers these files too.
4. **`loop status` reports throughput.** After its usual lines, `loop status` prints a throughput section for the selected window: issues merged per hour, seconds per stage and each stage's share of the window, turns and tokens per role, parks by rule, and the five slowest steps. `loop status --json` prints only this throughput section, as one JSON object. To supply the figures, every Claude and Codex session now records a `session` event with its role, agent, model, turns, and input, cached input and output tokens, as the agent reports them; a count the agent does not report is left out. A `parked` event now carries the rule of the last guard or merge refusal that preceded the park, where there was one.
5. **Steps record load and memory pressure.** Step start and end events, merges and parks in `.loop/events.jsonl` now carry `load`, the one-minute load average, and `pressure`, the macOS memory-pressure level, which is null on other systems or when the reading fails.
6. **Issues can declare a kind.** An issue may hold a `Kind: build` or `Kind: parallel` line; a missing or unknown kind means `build`. The loop runs at most one `parallel` issue beside the builds, without taking a `Parallel` slot, for work that cannot conflict with builds, such as documentation or research. A parallel issue still waits for its dependencies and, like any further build, for load and memory headroom. The board marks it `(parallel)`. The issue template and the shape skill describe the line.
7. **Sessions get `loop check` and a test budget per step.** In a build tree, `<plugin>/bin/loop check` runs the issue's locked tests and the test files changed since the session's start commit through the Test files command, or the Test command when none is set, then runs the Check command. It prints one line when everything passes, or the failing command and at most the last 60 lines of its output. With a Test files command and no test files selected, it skips the tests and still runs the Check command.

   The session instructions now set a test budget per step: the test writer runs only its new tests, the builder runs `loop check`, the reviewer reads the Stop hook's result and runs checks only when a finding needs one, and the end-of-loop pass runs only its candidate tests. The budget is an instruction to the model, not a rule the guard enforces. The guard already refused the full Test command in these sessions; its refusal now points to `loop check`.
8. **Shaping lists the paths an issue will touch.** The shape skill now runs `python3 <plugin>/scripts/shapecheck.py <draft-file>` on each draft. The script reads the backticked names in the draft and lists the tracked test files that refer to them, including helpers, fakes and runners, together with any named file on the stops list. The shaper writes this list into `## Protected paths this issue may change` before your approval. The script exits non-zero above 20 files, and the shaper then splits the issue. With `--issues <issues-json>`, it also warns when one issue has more than two dependants or a dependency chain is deeper than three links.

   When a build starts, the loop runs the same check against the loop branch. If it finds paths, it posts them on the issue and in the build note, and names those that still lack approval. The report grants no permission.
9. **A default branch that cannot be merged is reported.** When the default branch does not merge into the loop branch, the loop writes one line to `loop.out` naming the conflicting files, repeats it only when the message changes, and records a `default-merge-failed` event. While the conflict lasts, the final pull request carries a `Default branch merge` section with the same message. The loop keeps building and merging meanwhile.
10. **`loop.json` and `loop.local.json` stay protected.** In 3.0.0, a project's own `Protected paths` list replaced the defaults and could leave both files open to change. Both files at the repository root are now on the stops list whatever the list holds; a file with the same name in a subfolder is not. An issue that must change one still names it under `## Protected paths this issue may change`.
11. **Guard and merge-check fixes for locked tests.**
    - A locked test replaced by a symlink, or whose file mode has changed, is now refused at merge as `locked test modified: <path>`, even when its contents compare equal. The guard also refuses an edit that resolves to a locked test through a path it would not otherwise treat as a test.
    - When a session's start commit cannot be read, the guard now keeps existing tests locked instead of treating every tracked test as new. The builder's Stop hook no longer lets the session finish when it cannot select test files; it asks the builder to restore the session's start commit.
    - With a Test files command set, the guard now refuses, under rule `full-test`, a Test files command that names every test module in the worktree or names none, since either runs the whole suite. It recognises Python module names and ignores shell redirections when it compares. A command that names only some test modules is still allowed.
12. **Smaller changes.**
    - Setup's dry run prints one line per `PLAN.md` section, with its heading, line count and proposed home, instead of the full text. A real run still files the inbox issue with every section in full.
    - Setup now writes a whole-number setting moved from `AGENTS.md`, such as `Parallel`, as `2` rather than `2.0`. A `loop.json` written by the 3.0.0 setup is still read.
    - Test files with a space in their name are now selected correctly, and a name such as `test something.py` counts as a test.
    - Each build process now receives `LOOP_TEST_WORKERS`, the processor count divided by `Parallel`, at least one. The kit's own test runner reads it to share the processor between builds that test at once; a project's test command can read it too.

## What was tested

All 1,034 tests in the kit's suite pass on macOS. Each change comes with new tests, among them the merge cadence across a restart, the run on the loop branch head when a due full suite fails, background priority with a fake `taskpolicy`, the throughput report from fixture events, and each guard fix. The kit's own test suite now reuses its fake commands and shares processor workers across builds, to reduce the load when the loop builds the kit; that effect has not been measured.

Not proven yet: no loop run has used the merge cadence, issue kinds or the build-time shaping check. The load figure in item 2 comes from setting the class by hand, not from this release. The next run on this repository is the measure.
