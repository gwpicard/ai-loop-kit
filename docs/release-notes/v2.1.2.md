# AI Loop Kit 2.1.2

This release allows Codex sessions to write to the per-user cache folder on macOS, and to further folders a project names in a new setting. In 2.1.1 the Codex sandbox refused writes to the per-user cache folder and to `~/Library/Caches`, and in a Swift and Xcode project the Codex test writer stopped with write errors.

Only projects that set a role to `codex` in `AGENTS.md` are affected. Projects that use Claude for every role do not change.

## Updating

1. In Claude Code, refresh the marketplace, then update the plugin:

       /plugin marketplace update ai-loop-kit
       /plugin update ai-loop-kit@ai-loop-kit

2. Start a new Claude Code session so that the new plugin loads.
3. A loop that is already running keeps the version it started with. To move it to 2.1.2, stop it from the project root, wait until `.loop/loop.pid` is gone, and start it again:

       <plugin>/bin/loop stop
       mkdir -p .loop && nohup <plugin>/bin/loop run > .loop/loop.out 2>&1 &

4. If your build tool keeps a cache elsewhere, such as under `~/Library/Caches`, add it to the new setting under `## Loop` in `AGENTS.md`. Commit the change and let it reach the loop branch, because each build reads the setting from its own checkout. For SwiftPM:

       Codex writable roots: ~/Library/Caches/org.swift.swiftpm

Nothing else changes, and the update does not touch the files in `.loop/`.

## What changes

1. **A Codex session can write to the temp and cache folders.** Besides the worktree and the repository's git folder, a Codex session may now write to the folder named by `$TMPDIR` in the loop's environment, on every platform, and on macOS to the per-user temp and cache folders that `getconf DARWIN_USER_TEMP_DIR` and `getconf DARWIN_USER_CACHE_DIR` report. Under 2.1.1 a Codex session could not write to the per-user cache folder, and in one Swift and Xcode project the test writer stopped with errors such as the following.

       <unknown>:0: error: unable to make temporary file: Operation not permitted

2. **A new `Codex writable roots` setting names further folders.** It takes a comma-separated list, written like `Protected paths`, and a leading `~` is expanded. Use it for a build tool's cache in your home folder, such as the SwiftPM cache. The default is empty.

A folder that does not exist is left out, and a folder named twice is listed once. A `codex exec resume` session gets the same folders as the first session. The kit's guard hook still checks every command a Codex session runs.

## What was tested

All 684 tests in the kit's suite pass on macOS. New tests start a Codex session against a stand-in `codex` command and read the folders it was given: the temp folder, the two macOS folders, the folders from the setting, a folder that does not exist, a failing `getconf` and a resumed session.

On a Mac, the real codex-cli 0.166.0 sandbox was given the 2.1.1 folders, and then the 2.1.2 folders with `~/Library/Caches` added as the setting would add it. A command run inside the sandbox attempted to write a file in the temp folder, the per-user cache folder and `~/Library/Caches`. With the 2.1.1 folders only the temp folder could be written. With the 2.1.2 folders all three could be written. Without the setting, `~/Library/Caches` stays refused.

Not proven yet: no Swift or Xcode build has run inside a Codex session on 2.1.2. The field error `xcodebuild: error: Could not resolve package dependencies:` is expected to need the SwiftPM cache in the setting, as in step 4, but that has not been confirmed.
