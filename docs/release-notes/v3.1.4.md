# v3.1.4

This release moves the loop's temporary folder out of a hidden folder, so a project that rejects paths beginning with a dot should no longer fail only inside the loop. It also gives each build, drain and end-of-loop pass a cache folder that survives the build's worktrees, so a project can keep compiler output, such as Xcode's DerivedData, from one build to the next.

The temporary folder change applies to every project. The cache folder is available to every project, but it saves time only for a project whose commands write to it, as described in item 2.

## Updating

1. In Claude Code, refresh the marketplace, then update the plugin:

       /plugin marketplace update ai-loop-kit
       /plugin update ai-loop-kit@ai-loop-kit

2. Start a new Claude Code session so that the new plugin loads.
3. In the commands below, `<plugin>` is the installed plugin folder, the one that holds `bin/`. A loop that is already running keeps the version it started with. To move it to 3.1.4, stop it from the project root, wait until `.loop/loop.pid` is gone, and start it again:

       <plugin>/bin/loop stop
       mkdir -p .loop && nohup <plugin>/bin/loop run > .loop/loop.out 2>&1 &

This release needs no setup run and adds no setting to `loop.json`. Settings, labels, parked issues, the loop branch and its pull requests carry over unchanged.

The loop now creates two folders beside the project, next to `.loop-worktrees`: `loop-tmp` and `.loop-cache`. On a Mac, if you excluded only `.loop-worktrees` from Spotlight rather than the folder that holds your projects, add these two as well.

## What changes

1. **Build temporary folders no longer sit inside a hidden folder.** Each build's temporary folder moves from `../.loop-worktrees/loop-build-*` to `../loop-tmp/loop-build-*`, still beside the project, and the loop still removes it after the build. The loop passes this folder as `TMPDIR`, `TMP`, `TEMP` and `LOOP_TMPDIR` to sessions and to the Test, Check, Prepare and Smoke commands, so the loop adds no component that starts with a dot to any of those paths. The end-of-loop pass now runs with its own temporary folder there too, instead of the temporary folder from the loop's own environment. Build worktrees stay in `.loop-worktrees`.

   The loop still replaces any `TMPDIR` in the environment it starts from. A project that rejects hidden paths also needs the path of the folder that holds the project to contain no hidden component.

   On 26 November, in a field project, a Swift app that rejects any path component beginning with a dot failed 71 tests that write temporary files at every merge, on the issue branch and on the loop branch alike. Three approved issues parked after merges of about 16 minutes each. The same test class failed with `TMPDIR` under a dot folder and passed without one.

2. **Builds can reuse a cache folder across worktrees.** Each build, drain and end-of-loop pass, and the session that writes the loop's pull request summary, receives `LOOP_CACHE_DIR`: an existing folder under `.loop-cache/<project>/`, beside the project. A build keeps one folder for all its sessions and commands, including the checks and merge tests that run in scratch trees. Codex sessions may write to it.

   An exclusive lock holds the folder until the operation ends, so operations that run at the same time use different folders, named `1`, `2` and so on. A later operation reuses a free folder, even when its previous holder exited without cleaning up.

   The loop sets no tool variable itself; a project points its own tools at the folder. For an Xcode project, a Makefile can use the cache and fall back to `.build/DerivedData` when `LOOP_CACHE_DIR` is unset or empty:

       DERIVED := $(if $(LOOP_CACHE_DIR),$(LOOP_CACHE_DIR)/DerivedData,.build/DerivedData)

   Then pass the quoted path to `xcodebuild` with `-derivedDataPath "$(DERIVED)"`.

   The loop never deletes these folders, so they hold whatever the project stores in them, and operations that overlap each fill a folder of their own. To reset a cache, delete its numbered folder while no build, drain or pass is using it, for example while the loop is stopped.

   On 25 November, in a field Xcode project on 3.1.2, the compile step took 145 to 470 seconds in builder worktrees and up to 622 seconds in test-writer worktrees under load, against 23 to 29 seconds in merge trees. Every worktree and scratch tree started with an empty DerivedData, and one issue compiled the project from nothing at least four times.

## What was tested

All 1252 tests in the kit's suite pass on macOS, run from a fresh single-branch clone with the default temporary folder. New tests check that sessions and the Test, Check, Prepare and Smoke commands receive a temporary path with no hidden component, including in the end-of-loop pass and after a failed Smoke command, and that the folder is removed afterwards.

Other new tests check that one build's commands share one cache folder across its worktree and scratch trees, that a file in it survives the build and reaches the next build, that concurrent builds receive different folders, that the drain, the pass and the summary session hold their own folder, and that Codex sessions may write to it.

Not proven yet: neither change has run in an unattended loop. How much of an Xcode build the cache saves across different worktree paths has not been measured.
