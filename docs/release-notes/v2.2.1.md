# AI Loop Kit 2.2.1

This release cuts the time the loop spends waiting instead of building: it waits for memory only at critical pressure, stops locking test helper files, and holds off draining while a recent park awaits a reply.

Every project gets these changes. The memory changes apply on macOS, and the full-test rule applies when a `Test files command` is set. They matter most on a Mac whose memory pressure often reads "warning", and in projects whose issues change test helpers or depend on one another.

## Updating

1. In Claude Code, refresh the marketplace, then update the plugin:

       /plugin marketplace update ai-loop-kit
       /plugin update ai-loop-kit@ai-loop-kit

2. Start a new Claude Code session so that the new plugin loads.
3. In the commands below, `<plugin>` is the installed plugin folder, the one that holds `bin/`. A loop that is already running keeps the version it started with. To move it to 2.2.1, stop it from the project root, wait until `.loop/loop.pid` is gone, and start it again:

       <plugin>/bin/loop stop
       mkdir -p .loop && nohup <plugin>/bin/loop run > .loop/loop.out 2>&1 &

4. If an issue is parked because it changes a test helper, reply `yes` on the issue to queue it again.
5. If your project has test files that are recognised as tests only because they sit in a test folder, rename them to a test name, such as `test_example.py` or `example.spec.ts`. Otherwise the test lock no longer protects them and the Test files command no longer runs them.

This release needs no setup run. Settings, labels, parked issues, the loop branch and its pull requests carry over unchanged.

## What changes

1. **Memory waits only at critical pressure.** On macOS, a session or test command now waits for memory only when the system reports critical pressure and more than one build is running. Each wait lasts at most 10 minutes; then the step starts and `loop.out` says so. A build running alone never waits for memory, a merge never waits for memory while it holds the merge lock, and memory waits no longer count against the build's time limit. Memory pressure holds back another build only at the critical level; the limit on processor load still applies. Each wait is recorded in `.loop/events.jsonl` as a `memory-wait` event.

   Before, every session and test command waited whenever pressure was above normal. On one Mac, where that was the usual state, the waits took more than four hours of a seven-hour run, held a finished merge for 37 minutes and led to a build being stopped at its time limit.
2. **The test lock covers test modules, not test support files.** The lock still protects files named like tests, such as `test_*.py`, `*.spec.ts` and `conftest.py`, that existed before the build, and the test writer's tests; a builder may still edit test files it adds itself. The lock no longer covers other files in a test folder, such as helpers, fakes, runners and fixture data; protected paths, manifests and settings still need the issue's approval. `loop report` and the `## What changed` section list them as "test support files changed", and the Test files command is never given a support file as a test to run.
3. **A yes approves every test file the question names.** When a park asks whether the builder may change existing test files and a collaborator replies yes, the loop allows every test file named in the question. Before, a yes allowed a file only when the question named exactly one. Files named only in the recommendation do not count, and a protected path is never allowed.
4. **No drain while a recent park blocks the queue.** When nothing is building and every `ready` issue depends on an open issue labelled `needs-user`, the loop keeps reading replies and holds off draining until an hour after the latest of those parks. The board shows how many minutes remain. After that, the loop drains as before.
5. **`loop stop` says what it does, and `loop stop --now` stops at once.** `loop stop` starts nothing new and ends once the running builds finish their issues; its message now says so. `loop stop --now` ends the running builds immediately and returns their issues to `ready`. It does not count them as crashes, so a stop no longer parks an issue. Builds now always run in a process of their own, also with `Parallel: 1`, so that a stop can end them.

       <plugin>/bin/loop stop --now

6. **The full Test command is reserved for merge in every role.** When a Test files command is set, test-writer and end-of-loop pass sessions may no longer run the bare Test command either; the refusal names the command to use. Before, the rule covered only builder and reviewer sessions.

## What was tested

All 861 tests in the kit's suite pass on macOS.

The same four small issues as for 2.2.0 were built twice in a new repository with Codex in every role. Each issue merged in about four minutes, and all four after 16 and 17 minutes, close to the four to five minutes per issue measured for 2.2.0. No issue parked, crashed or waited for memory. Those issues did not change test helpers or depend on one another, so the runs show that the build path still works, not the gains above.

Not proven yet: the gains on a project with high memory pressure and dependent issues. A session can still run the whole suite by naming every test module in the Test files command; on the second run, end-of-loop pass sessions did this after the guard refused the bare Test command.
