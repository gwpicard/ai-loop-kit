# AI Loop Kit 1.6.0

AI Loop Kit 1.6.0 lets a run build many pieces onto one loop branch while you are away, so you review one final pull request into `main`, and it lets setup start a project from an empty folder.

**Some of this release depends on your settings.** The loop branch features apply only when the loop section of `AGENTS.md` sets `Base branch:` to a branch other than `main`, and the run merges pieces itself only when it also sets `Base merges: run`. The `Agent model:` and `Agent effort:` settings and doctor's Test run in the Codex sandbox apply only to projects with `Agent: codex`. Setup from an empty folder matters only for a new project.

Everything else reaches every project: the uv requirement, the stricter dependency and check-settings rules, `Depends on:`, the build-time dependency fixes and the smaller corrections. Walk-away runs, loop branches and the Codex backend are still previews.

## Updating

1. Install uv if you do not have it. The kit's own commands and hooks now start their Python through uv, and without uv they refuse. Run one of:

   ```text
   brew install uv
   curl -LsSf https://astral.sh/uv/install.sh | sh
   ```

2. Update the plugin, either from a terminal:

   ```text
   claude plugin update ai-loop-kit@ai-loop-kit
   ```

   or in Claude Code: run `/plugin`, open the **Installed** tab, select **ai-loop-kit** and choose **Update now**.

3. Run `/reload-plugins`, or start a new session, so Claude Code loads the new version.

The kit needs git 2.38 or later; it does not check the version itself. Your issues, pieces and loop settings stay as they are, and every new setting is optional.

Two rules are stricter than before, and they also apply to pieces you have already shaped. A build that changes the version of an existing dependency is refused unless the spec names that dependency under `New dependency:`. Ready refuses a piece whose Contract names a check-settings file unless the spec has `Settings: may change` in its `## Judge` section.

To use a loop branch, create the branch from `main` and push it. Then add `Base branch: <branch>` to the loop section of `AGENTS.md`, and `Base merges: run` if the run should merge pieces into it, and merge that change into `main`: the kit reads its settings from `main`. If a Quality command names `origin/main`, change it to use the `LOOP_BASE` environment variable, which the kit sets to the base branch; doctor warns about this.

## What changes

1. **Walk-away runs onto a loop branch.** With `Base branch: <branch>`, ready judges each piece against that branch and the piece pull requests target it. At the end of each run, one pull request brings the branch into `main`. It lists the pieces in merge order, names the check settings and protected paths each piece changed, and says "incomplete" while pieces still wait.

   With `Base merges: run` as well, the run merges each gated piece into the branch itself and moves it to done. It never merges into `main`. It leaves a piece for you when its contract review has findings, when the branch moved after the gate passed, when GitHub refuses the merge, or when the piece changes `.github/`, `.githooks/` or `AGENTS.md`, because those run code or change the loop's rules. After you merge such a piece, `gate.py sync` marks it done and updates the final pull request.

2. **Pieces can wait for other pieces.** An optional sixth line in a spec's `## Risks` section, such as `Depends on: 12, 15`, names pieces by number. The run then holds the piece until those pieces are done, builds the next piece whose dependencies are done, reports each held piece with its reason, and goes on with the rest. A piece that comes back holds the pieces that depend on it. This works with or without a loop branch.

3. **Setup can start a project from an empty folder.** `/ai-loop-kit:setup` now makes what is missing: the git repository, a private GitHub repository after you agree its name, the first commit with the loop settings, and the first push of `main`. Where your GitHub plan allows it, it also turns on branch protection. A new project needs no setup pull request.

   When Prepare is `uv sync` and the folder has no `pyproject.toml`, setup writes a minimal one, with pytest as a development dependency, and `uv.lock`, so the first checks can run. Doctor then reports that the project has no tests yet and points you to a scaffold piece, also for a unittest project without a `tests` folder.

4. **The kit runs its own commands on Python 3.13.** uv finds or installs Python 3.13 for the kit's commands and hooks, so the Python on your computer no longer matters for them. Your project's Test, Prepare and Quality commands still use the project's own Python. If the kit cannot start, its hooks now refuse the tool call instead of letting it through.

5. **Dependencies added during a build are installed.** When a build changes a dependency file, the run runs Prepare again, outside any sandbox, before the judge. Agent sessions keep uv's cache inside the build folder, so `uv run` works where a session cannot write to your home folder, as in the Codex sandbox. Agent sessions also no longer inherit standard input, which could leave a Codex session waiting until its idle limit. The cache change covers uv only, not npm or pip.

6. **Codex model, effort and sandbox check.** `Agent model:` and `Agent effort:` choose the Codex model and reasoning effort for every role, and ready records them so a run cannot change them halfway through a piece. `gate.py doctor --walk-away` now runs the project's Test command once inside the Codex sandbox and names what blocked it.

7. **Dependency changes need the spec.** The gate already refused new dependencies that the spec did not name. It now also refuses a changed version constraint on an existing dependency, in any `package.json` or `pyproject.toml`, unless the spec names it under `New dependency:` with a reason. The refusal tells the builder that only the spec can allow it, so the piece comes back after one attempt instead of three.

8. **Check settings need `Settings: may change`.** Ready refuses a piece whose Contract or Exit files name a check-settings file, such as a workflow under `.github/`, unless the spec has `Settings: may change` in its `## Judge` section. Before, such a piece was built and then refused at the gate.

9. **Smaller corrections.**
   - A piece is no longer sent back with a wrong bar because another piece's judge landed in the same folder, or because a helper beside the judge changed on the base. A piece whose tests already pass on a moved base comes back as `spec-unclear` with the cause `already-satisfied`.
   - Settings merged on GitHub, such as `Base branch:`, are read from a fresh `main` before ready, doctor and the run use them.
   - The false "kept worktree" warnings are gone: for a piece whose pull request waits for you, and for the ready gate's own copy of `main` when only test caches are left in it.
   - An environment hand-back gives the tool evidence first, then "The builder said:" with the builder's own explanation.
   - Ready's refusal for a `(stays)` item that fails on the base says that the item must hold on the base now, not after the pieces it depends on land.
   - On a free plan, doctor says that branch protection is not available for a private repository and that the guard and the gate still hold, instead of "unknown".
   - When setup's bootstrap refuses after it has made something, it first says what it made.
   - Writing a judge no longer fails on test caches in an ignored `node_modules`, or on `uv run` reinstalling the project in an ignored `.venv`.
   - The guard lets an agent delete a remote branch whose tip is already in `main`. It still refuses `main`, `master`, `stable`, `piece/` branches, tags, unmerged branches and squash-merged branches.

## What we tested, and what is not proven yet

- All of the kit's own checks pass on Linux and macOS.
- On an earlier release candidate, setup in an empty folder, on a new private repository, reached doctor with no failures and two warnings, for no tests yet and the plan limit, and with no pull request made by hand. An attended run on Claude then built a scaffold piece and a feature piece, each on its first attempt; Claude wrote the feature piece's judge.
- On the final release candidate, a walk-away run on Codex built three new pieces onto a loop branch in 7 minutes. The piece that adds a dependency passed on its second attempt, after Prepare installed the dependency; the piece that waits for it and a workflow change each passed on the first. The run held the workflow change for the maintainer, and after that merge, `gate.py sync` updated the final pull request.
- An earlier walk-away run on Codex built a small real project onto a loop branch and finished all 8 of its pieces. It needed fixes by hand, and those fixes are in this release.
- Not proven yet: installing 1.6.0 fresh from the marketplace, or updating to it from 1.5.0; a walk-away run on Claude in a real project; npm and pip caches in the Codex sandbox; merge queues or required checks on the loop branch; branch protection on a private repository, which needs a paid GitHub plan. The preview field round and the test that stops a run during its review step are planned for 1.7.
