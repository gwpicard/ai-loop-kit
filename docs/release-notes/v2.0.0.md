# AI Loop Kit 2.0.0

Version 2 replaces the kit with a continuous factory: you shape work into GitHub issues and approve it once, and a loop on your computer builds, reviews and merges each issue while you are away.

This is not an upgrade of 1.x. It is a new design under the same plugin name, and it replaces version 1 entirely. Every project that used version 1 needs the steps under Updating before the loop will run. Nothing from version 1 is read: there are no `state:` labels, no gate, no judges written at shaping and no dashboard.

## Updating

1. In Claude Code, refresh the marketplace, then update the plugin:

       /plugin marketplace update ai-loop-kit
       /plugin update ai-loop-kit@ai-loop-kit

2. Remove the old extras plugin. Version 2 has no extras plugin, and `ai-loop-kit` is now the only plugin in the marketplace:

       /plugin uninstall ai-loop-kit-extras@ai-loop-kit
3. Start a new Claude Code session so that the new plugin loads.
4. In each project, put a `## Loop` section in `AGENTS.md`. Only the `Test command:` line is required. These optional lines are the most useful:

       ## Loop
       Test command: <the command that runs your tests>
       Test files command: <a command that runs only some test files, with {files} for their paths, for example pytest {files}>
       Prepare command: <installs what a fresh checkout needs, for example npm ci>
       Check command: <your lint and other guardrails>
       Parallel: 3
       Protected paths: <paths the loop must not change>

   `Parallel: 3` is only an example: the default is 1. Version 1 settings in the old section, such as `Base branch` and `Keep limit`, are ignored. The full list of optional lines is in `kit/README.md`.
5. Ask Claude to set up the loop. Setup creates the labels, the loop branch (`loop/main` by default), a pinned `Factory` issue and a `.lite/` line in `.gitignore`, which you commit yourself. It also runs your Test command on a fresh copy of the loop branch. Running setup again is safe. Below, `<plugin>` means the installed plugin folder, which holds `bin/`.

Open version 1 work does not carry over. Use the shape skill to turn it into issues with acceptance criteria and label them `ready`. Version 1 `state:` labels and piece files are not read.

Existing `.loop/` data is not read by version 2 and is not changed. Version 2 keeps its own runtime state in `.lite/`.

## What changes

1. **A continuous factory, driven by labels.** The shape skill turns an idea or inbox issues into issues with acceptance criteria and dependencies, asks one batch of questions, records decisions in `PLAN.md` and, on your single approval, labels the issues `ready`. A plain Python loop then builds them without you. You can shape while it runs, and new issues join the queue. The loop never asks for input: it parks an issue only for a decision that `PLAN.md` reserves for a person, and carries on with the rest. It stops after 12 idle hours, or when you run `<plugin>/bin/loop stop`. To start it, ask Claude or run this from the project root:

       mkdir -p .lite && nohup <plugin>/bin/loop run > .lite/loop.out 2>&1 &

2. **A fixed flow for each issue.** A test writer commits failing tests from the acceptance criteria before any code exists, and each must fail by assertion. A builder then makes them pass. A fresh reviewer session checks every acceptance criterion with evidence and gives a verdict that names the commit it reviewed. The loop merges only through `merge.py`, and only the reviewed commit, or a conflict-free merge of it with the current loop branch, after the full Test command passes on that exact commit. A builder cannot end its session while the Test or Check command fails.

3. **Parallel builds.** `Parallel: N` builds up to N issues at once, each in its own worktree and process. The loop starts another build only while the machine has spare load and memory, and merges queue behind one lock. The default is 1. A fast path lowers the cost of each build: `Test files command` runs only the relevant tests while the builder works, and the full Test command runs twice per issue, once when the builder finishes and once at merge.

4. **An end-of-batch check and standing approvals.** When the queue drains, one pass reads the whole batch: it runs your `Smoke command` if set, reviews drift from the plan, red-teams the code, reviews readability, records lessons and files one issue of simplifications. A defect counts only if it comes with a failing test that a second session confirms. A confirmed defect is queued as `ready` only if a paragraph under `## Standing approvals` in `PLAN.md` positively allows it. Otherwise it goes to the inbox. `Defect rounds` (default 2) caps how many times this repeats without a merge of an issue you queued. The loop then opens one pull request into your default branch, which you merge yourself.

5. **The board is on GitHub.** A pinned `Factory` issue shows what is building, what needs you, the queue, what has landed, the open pull request and the last pass. To answer a parked issue, reply on it: the loop queues it again and gives your reply to the next build. A reply of "yes" from a collaborator to a park that names one test path lets the loop add that path itself.

6. **Safety.** A guard hook refuses pushes to the default branch, force pushes and recursive deletes everywhere, and also `gh`, `git push`, `git merge` and branch switches inside the loop's sessions. The hook matches the text of commands, so it is an early warning and can be routed around. The lines that hold are in code: `merge.py` refuses a diff that touches a protected path, a workflow, a lockfile, a package manifest, a settings file or an existing test unless the issue names that path. It also locks the test writer's tests against the builder. The loop builds only issues that a collaborator with write access labelled `ready`. Sessions start with project-only settings and a strict MCP configuration, so they do not inherit your plugins and MCP servers. The loop never merges into the default branch. Branch protection on that branch remains your job.

7. **What was removed, and why.** The gate and its state machine, judges written and frozen at shaping, the dashboard server and run page, the preview tools (measure, critics, mutation, researcher), the `kit-python` runner and the `extras` plugin are gone. Each field failure in version 1 had added a state, a reason or a setting, and each rule needed more rules at its edges. Writing and proving judges ran the full suite about three times per piece. The kit's Python shrinks from about 8,600 lines to about 2,100. Version 1 stays in git history and under the `v1.7.0` tag.

## What was tested

The kit's own suite of 307 tests passes, and `tests/run-all.sh` passes with the repository's house rules. Four smoke runs in a private repository covered fix rounds, parks and replies, a planted defect that the end-of-batch check found and the loop fixed, and three issues built at once.

One trial on a real project with a test suite of about 1,500 tests built and merged all 8 issues it was given. The end-of-batch check found 16 confirmed defects by itself, and the loop merged 15 of them during the trial. The person was asked three genuine questions, and each parked while other work continued. Issues took about 50 minutes each before the fast path existed, and 19 to 25 minutes with the fast path and three builds at once. The same project's version 1 history, recorded in an earlier review, shows more attended runs and more backward moves. This is one trial, and the comparison is indicative, not controlled. The trial ran before the `Defect rounds` cap existed.

Not proven yet:

- Visual work and other behaviour that only a person can see stay unchecked unless the issue gives an agent a way to check it, such as a render or a measurement.
- Notifications are not built. Watch the board.
- The briefs tell sessions never to ask and to record deviations, but code does not enforce that, and the reviewer and the end-of-batch check can miss a defect.
- Only Claude is supported as the agent.
