# AI Loop Kit 2.1.0

This release adds a summary to the loop's final pull request that you can read before you open the diff, requires the tests and reviews of a run to show evidence, and lets you choose Claude or Codex for each role. Codex is a preview.

The agent choice is available in every project, but nothing changes until you set a role to `codex`: each role defaults to `claude sonnet`, and the older `Builder model` and `Reviewer model` lines keep working. The other changes apply to every project from its next loop start.

## Updating

1. In Claude Code, refresh the marketplace, then update the plugin:

       /plugin marketplace update ai-loop-kit
       /plugin update ai-loop-kit@ai-loop-kit

2. Start a new Claude Code session so that the new plugin loads. From this version on, the kit refuses to run in a session that still runs an older kit than the one a project was set up with, and tells you to restart Claude Code.
3. A loop that is already running keeps the version it started with. To move it to 2.1.0, stop it from the project root, wait until `.loop/loop.pid` is gone, and start it again:

       <plugin>/bin/loop stop
       mkdir -p .loop && nohup <plugin>/bin/loop run > .loop/loop.out 2>&1 &

You do not need to run setup again. This release adds no labels and no files to commit. The first setup or loop start with 2.1.0 writes the kit version to `.loop/kit-version`, a file inside the `.loop/` folder that setup already lists in `.gitignore`. Your settings stay under `## Loop` in `AGENTS.md`. The loop skill now asks you to confirm the agent and model for each role before every start.

## What changes

1. **The final pull request opens with a summary.** One read-only session per batch writes three sections that come first in the body: `## Summary`, with small visuals next to the text they support; `## Evidence`, which names for each merged issue the test that failed before and passes now, or the command output that changed; and `## Merge danger`, which says whether the merge is easy to undo or not, names each change that is not, and gives the blast radius. When it is unsure, it says the merge cannot easily be undone.

   After them come `## Hands-on checks`, `## Decisions to confirm`, `## Landed` and the end-of-loop pass report.

   The session runs only when the loop branch has new merges since the last summary; a refresh reuses the saved one. If the session fails, the body is built without it, with one line saying the summary did not run, and the loop carries on.

2. **Hands-on checks and decisions to confirm are listed for you.** An issue can now carry a `## Hands-on check` section: numbered steps a person follows in the real product, each with the result to expect. The shape skill asks for them for every piece a person sees or touches. The final pull request lists them as unticked boxes under the issue they belong to, and a refresh keeps the boxes you have ticked. No session ticks a box, and the loop never waits for one.

   The `## Decisions to confirm` section copies each line the loop added under `## Deviations` in `PLAN.md` on the loop branch, so you confirm the loop's choices in one place before you merge.

3. **Tests drive the entry point a person uses.** When a criterion describes something a person triggers, the issue template and the shape skill now ask for the entry point: the keys pressed, the menu item chosen, the command run or the HTTP route called. The test writer is told to drive that entry point instead of calling internal functions, and to use more than one example input where layout or order could matter. The reviewer returns CHANGES for a test that does not.

   This responds to a run in which the tests stayed green although a person found about 33 defects by hand on first real use.

4. **Only verified findings become fixes in the review.** Each numbered fix must give `file:line`, a concrete failure scenario and the fix; an uncertain finding becomes a follow-up marked "unverified", not a fix. For every test the builder added, the reviewer states whether it would fail without the change, and a test that cannot fail is a CHANGES item.

   The reviewer also follows the code path from the entry point to check wiring that tests do not reach, such as registration, menus, routes and configuration, and ends with a short "Checked and sound" list. The builder is told that a fix for a review finding comes with a test that reproduces it through the real entry point, or the build notes mark the fix as unverified.

5. **The end-of-loop pass validates rubric findings before it files them.** The existing confirm session now also checks each rubric finding against the code at its `file:line` on the loop branch, and accepts it only when the code shows the problem and the project's rules make it one. A finding without `file:line` is rejected. Rejected findings appear in the pass report with their reason. The pass still starts at most nine sessions. If the confirm reply cannot be read, rubric findings are filed marked "(not validated)".

   The drift review also reports any source folder or build target changed in the batch that neither the Test command nor the Check command builds, type-checks or tests, and the shape skill asks once per project whether those commands cover every target and source folder.

6. **The kit refuses to run when it is older than the project's setup.** Setup and the loop record the running kit's version in `.loop/kit-version`. If a later session runs an older kit, for example one started before a plugin update, setup, `loop run` and the new `loop check-version` stop before they change anything, print `refused: this session runs kit <old>, but this project was set up with kit <new>`, and tell you to restart Claude Code. The shape and loop skills run `loop check-version` first.

   Versions compare as numbers, so 2.10.0 counts as newer than 2.9.0. A kit older than 2.1.0 never runs this check, so the protection starts with this release.

7. **Choose the agent and model for each role.** Four new lines in `## Loop` take an agent and a model each: `Builder`, `Test writer`, `Reviewer` and `Pass`, for example `Builder: claude sonnet`. The pass line also covers the pull request summary session. A value that is not exactly two words is refused with the line named. Setup prints one line per role, and the loop skill shows the four before every start and asks once whether to change any.

8. **Codex can run any role (preview).** With `Builder: codex <model>`, for example, the loop starts `codex exec` in the role's worktree with the `workspace-write` sandbox, reads its reply and session id, and resumes the same session for a fix round.

   A Codex session is held to the same rules as a Claude one: the kit passes the guard and the stop check to Codex as hooks, and the guard refuses any Codex command or patch it cannot parse. The kit passes `--dangerously-bypass-hook-trust` so that an unattended run can use hooks, and the only hooks it runs are the two the kit writes from its own folder.

   A Codex builder or test writer that stops with failing tests, or with no new test file, is sent back within the same limits as a Claude one. Setup and the loop's start check the installed Codex for the `codex` command, its hooks feature and the flags the kit passes, and refuse, naming what is missing, when one is absent. On a Codex usage limit the session waits for the reset time in the reply, or 30 minutes without one, and resumes; there is no fallback agent.

9. **The board shows progress and what needs you.** The pinned `Factory` issue now has three sections: `Building now`; `Needs you`, which lists parked issues, the open pull request into the default branch, a failed merge of the default branch into the loop branch, and the notice about the defect rounds limit; and `Progress`, one line for each open milestone that still has an issue the loop is building or waiting on, with its closed and total counts and a link to its milestone page. Each section reads `Nothing.` when it is empty.

   The `Queue`, `To shape`, `Landed since the last merge` and `Last pass` sections are gone, because GitHub's milestones page shows progress and the final pull request carries the landed list and the pass report.

   Under `Needs you`, a dependency that waits on something the loop will never build is now listed with the action it needs: merge the named pull request, shape the issue or label it `ready`, or check the `Depends on` line.

10. **Setup keeps the preflight's failing output.** The preflight now also runs the Check command, writes the output of each command to `.loop/logs/preflight.log`, and on failure prints the last 20 lines of the failing command, the log path and the folder the checkout ran in. The temporary checkout now uses the resolved path of the temporary folder, so tests that compare paths behave as they do in the project folder.

11. **Fixes to the loop's own handling.**
    - A failed GitHub comment or board write after the loop claims an issue no longer leaves it marked `building` and stops the loop from ever exiting.
    - A lock file that names a live process owned by another user is now refused instead of overwritten.
    - After a build has crashed twice, been parked and then received an answer, it no longer parks again on its next crash.
    - Command output that is not valid UTF-8 no longer makes a passing Test, Check or Prepare command count as a failure.
    - The end-of-loop pass no longer files "none found", "No findings." or a decorated "none" as a finding.
    - A merged pull request named on a `Depends on` line now counts as done.
    - One test that counted polling sleeps now passes on Linux.

12. **Fixes to how the kit reads replies and issues.** A `TESTS:` block is now read correctly when its items carry a note after a backticked path, when a blank line follows the heading, when it uses Windows line endings, when the heading is bold or backticked, and when another block header follows it directly. The same applies to a `VERDICT:` line with bold, backticks or trailing punctuation.

    An issue's allowed paths and the protected paths now ignore a leading `./`, and a Windows-line-ending issue body keeps its allowed paths after a code fence. A blank line after `TESTS:` no longer produces an empty locked path that parks every issue.

13. **The guard, the stops list and test-file recognition cover more cases.**
    - The guard now refuses `rm` with a recursive flag after the path, a `git push` split over lines or followed by a closing quote or parenthesis, PGP private key blocks, Slack tokens that start `xoxa-`, `xoxb-`, `xoxp-`, `xoxr-` or `xoxs-`, and GitHub tokens with the `gho_`, `ghu_`, `ghs_` and `ghr_` prefixes.
    - It no longer refuses a path that merely ends in `gh`, such as `cat kit/scripts/gh.py`, or a `>` inside a quoted argument such as `awk '$1>5' README.md`.
    - A change to a lockfile or package manifest of more ecosystems, including Bun, npm shrinkwrap, Pipenv, Composer, Bundler, CocoaPods, Mix, Pub, Nix and Swift Package Manager, now parks the issue.
    - The kit now recognises `tests.py`, `test.py` and `conftest.py` as test files, and no longer treats `Contest.java` or `Latest.java` as JUnit tests.

## What was tested

The kit's own suite passes on Linux and macOS in continuous integration, and `tests/run-all.sh` passes with the repository's house rules. Each change above comes with tests that failed before it, or that check the new behaviour, run against a fake Claude, a fake `codex` and a fake `gh`.

A release smoke run on 17 November 2026 used a new, empty private repository set up with the kit from `main`. One issue, a line-count function with four criteria and one hands-on step, was built, reviewed and merged unattended in about one minute. The final pull request carried Summary, Evidence, Merge danger, Hands-on checks, Decisions to confirm, Landed and the end-of-loop pass report. The hands-on step was run by hand and gave the expected result.

Not proven yet: the Codex roles have not run against the real Codex, only against a fake `codex` in tests, so Codex is a preview.

The real Codex usage-limit text is unknown, so the limit wait reuses the pattern that detects Claude's limit message. The hook configuration the kit passes to Codex has not been confirmed to be accepted by a real Codex, and a Codex builder's ability to commit in its worktree and write under `.loop/` has no test. A real run with `Builder: codex <model>`, showing the guard block a refused command, is still to do. The smoke run used Claude for every role.
