# v3.1.5

This release moves the per-project cache folder out of a hidden folder, as 3.1.4 did for the temporary folder, and keeps the output of a failed drain, so the cause of a red loop branch can be found after the fact.

Both changes apply to every project. The cache move matters only to a project whose commands write to `LOOP_CACHE_DIR`.

## Updating

1. In Claude Code, refresh the marketplace, then update the plugin:

       /plugin marketplace update ai-loop-kit
       /plugin update ai-loop-kit@ai-loop-kit

2. Start a new Claude Code session so that the new plugin loads.
3. In the commands below, `<plugin>` is the installed plugin folder, the one that holds `bin/`. A loop that is already running keeps the version it started with. To move it to 3.1.5, stop it from the project root, wait until `.loop/loop.pid` is gone, and start it again:

       <plugin>/bin/loop stop
       mkdir -p .loop && nohup <plugin>/bin/loop run > .loop/loop.out 2>&1 &

This release needs no setup run and adds no setting to `loop.json`. Settings, labels, parked issues, the loop branch and its pull requests carry over unchanged.

A project that already points its tools at `LOOP_CACHE_DIR` needs no change, because the variable now names the new folder. That folder starts empty, so the first build in each cache folder fills it again, for example by compiling from scratch.

The loop does not delete the old `../.loop-cache/<project>/` folder and no longer uses it. When it finds one, it writes this line once to `.loop/loop.out`, after a timestamp and with the folder's full path:

    old cache folder <parent>/.loop-cache/<project> is unused and can be removed by hand

On a Mac, if you excluded `.loop-cache` from Spotlight, exclude `loop-cache` as well.

## What changes

1. **The cache folder no longer sits inside a hidden folder.** `LOOP_CACHE_DIR` now names a folder under `../loop-cache/<project>/`, beside the project, instead of `../.loop-cache/<project>/`. The loop adds no component that starts with a dot to the path; a project that rejects hidden paths also needs the path of the folder that holds the project to contain none.

   The loop still replaces any `LOOP_CACHE_DIR` in the environment it starts from. Locking, numbered folders and reuse work as in 3.1.4.

   On 26 November, a field Swift app that rejects any path component beginning with a dot failed 71 tests that write temporary files, which is why 3.1.4 moved the temporary folder. A tool or test that writes under the old cache folder could meet the same rule.

2. **A failed drain keeps its output.** The drain now writes the full output of the Prepare, Test and Check commands to `.loop/logs/drain.log`, replaced on each drain. When the drain fails, `loop.out` gets one line that names the log and quotes up to 20 failing lines, picked out as a failed merge does, or the last four lines of the log when it finds none.

   The `drain` event in `.loop/events.jsonl` carries the same reason. Both happen whether or not a final pull request exists.

   In the kit's own loop, the drain failed four times on 26 and 27 November. The first failures kept no output, and the same tests passed when run by hand. Once this change was in the loop, the log from the last failure named two failing tests, which led to the fix described under "What was tested".

## What was tested

All 1263 tests in the kit's suite pass on macOS, run from a fresh worktree with `TMPDIR` unset. New tests check that the cache path passed to sessions and commands has no hidden component, that an inherited `LOOP_CACHE_DIR` is replaced, and that an old `.loop-cache` folder is left untouched and named once in `loop.out`. Other new tests check the drain log and the failure line and event, with and without a final pull request.

Those two failing tests are kit cache tests that compared a path through a linked folder, such as macOS's `/var`, with its resolved form under `/private/var`. They passed at merge and failed in the drain. The earlier failures left no log, so they probably had the same cause, but that is not confirmed. Both now resolve the paths before comparing, and a new test runs them through a linked temporary folder. This changes no behaviour in a project.

Not proven yet: the drain log and the move of the cache folder have run only in the kit's own loop, where the drain log named the cause of the failures and the loop reported the old cache folder once; neither has run on another project.
