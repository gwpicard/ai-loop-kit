# AI Loop Kit 2.2.0

This release runs the full test suite once per issue instead of several times, records what the loop did and how long each step took, and adds `loop status` and `loop report` so that you can see what happened while you were away.

Every project gets these changes. The largest speed gain needs a `Test files command` under `## Loop` in `AGENTS.md`; without one, the targeted runs fall back to the full Test command, as before. Projects that queued confirmed end-of-loop defects as `ready` through `## Standing approvals` in `PLAN.md` now receive them as `inbox` issues instead.

## Updating

1. In Claude Code, refresh the marketplace, then update the plugin:

       /plugin marketplace update ai-loop-kit
       /plugin update ai-loop-kit@ai-loop-kit

2. Start a new Claude Code session so that the new plugin loads.
3. In the commands below, `<plugin>` is the installed plugin folder, the one that holds `bin/`. A loop that is already running keeps the version it started with. To move it to 2.2.0, stop it from the project root, wait until `.loop/loop.pid` is gone, and start it again:

       <plugin>/bin/loop stop
       mkdir -p .loop && nohup <plugin>/bin/loop run > .loop/loop.out 2>&1 &

4. Run setup once from the project root. It removes the `Defect rounds` line, which the kit no longer reads, and records the change and how to undo it in `.loop/migrations.log`. To see what it would change first, add `--dry-run`:

       python3 <plugin>/scripts/setup.py --dry-run
       python3 <plugin>/scripts/setup.py

5. If your Test command takes more than a minute, add a command that runs only the given test files, with `{files}` standing for their paths. For example, with pytest:

       Test files command: `pytest {files}`

Setup does not edit `PLAN.md`. A `## Standing approvals` section stays in place, and the kit no longer reads it. Existing labels, parked issues, the loop branch and its pull requests carry over unchanged.

## What changes

1. **The full suite runs once per issue, at merge.** The builder's Stop hook and the run before review now run only the issue's locked test files and the test files it changed, followed by the Check command. `merge.py` runs the full Test and Check commands once, after its path and test-lock checks, so a refusal for a protected path or a changed test no longer costs a full test run. The end-of-loop pass uses the Test files command to check whether each red-team test fails. When a Test files command is set, builder and reviewer sessions may not run the bare Test command; the refusal names the command to use instead.
2. **The loop records what happened.** `.loop/events.jsonl` now records the start and end of every step of an issue's build, with its duration and outcome, and the agent and model of each session that step runs. Parks, crashes, drains, stops and exits are recorded, and each end-of-loop pass is recorded as a whole, with its duration and counts. Every refusal by the guard or by `merge.py` carries a rule name, such as `test-lock`. Every line in `.loop/loop.out` and in each `.loop/logs/build-<issue>.log` starts with a date and time.
3. **`loop status` shows what happened while you were away.** From the files in `.loop/` alone, it shows whether the loop is running and what it is doing, which issues merged or parked and why, crashes, how often each rule refused something, the time spent in each stage, and the agents and models used. It covers the last 12 hours; `--since` takes a time, such as `09:00`, or a duration, such as `4h`.

       <plugin>/bin/loop status --since 4h

4. **`loop report` and a "What changed" section.** Before you merge the loop branch, `loop report` lists the folders and tests that the merged issues changed, flags changes to package manifests, deleted tests and the files with the most lines added and removed, and gives each issue's reason, review rounds, parks and duration. The pull request into your default branch carries the same text at the top. No model writes it.
5. **The board explains itself.** It shows how many minutes the current step has run, never lists a parked issue as building, says when the drain or the end-of-loop pass is running, gives the date of the next check, and names the parked issues that hold back `ready` issues when nothing is building.
6. **Confirmed end-of-loop defects arrive as `inbox` issues.** Each keeps its failing test. The `Defect rounds` setting and the standing approval that queued defects as `ready` are removed, so the pass no longer adds work to the queue without your approval.
7. **Fewer issues are parked when no decision of yours is needed.** A builder may now edit a test file that it created on its own issue branch; tests that existed on the loop branch and the test writer's locked tests stay protected. When free disk space is below 2 GB, the loop waits before it starts a build, and a "No space left on device" failure waits and retries once before it counts as a crash. Each build has its own temporary folder, removed with its worktree.
8. **Session instructions repeat less.** The guidance that every session shares is now kept in one file and added to each session's instructions, and sentences that repeated rules the guard already enforces are removed. A reviewer receives the builder's BUILT and DEVIATIONS blocks rather than its whole report. A builder restarted after a park or a crash is pointed to the issue's earlier review rounds. Reviewers file at most two follow-up issues per issue, and none marked unverified.
9. **Setup previews and records its changes.** `--dry-run` shows every change setup would make and makes none. Each change setup makes is recorded in `.loop/migrations.log` with how to undo it. When the loop starts, it names any setting under `## Loop` that the kit does not recognise.
10. **Fixes.** A reviewer follow-up that begins with a name in backticks keeps its full text; before, the issue was titled with that name alone.

## What was tested

All 759 tests in the kit's suite pass on macOS and Ubuntu.

The same four small issues were built in a new repository with Codex in every role, once with 2.1.2 and once with 2.2.0. The test suite was made to take about a minute, and a counter recorded each full run.

| Measure | 2.1.2 | 2.2.0 |
|---|---|---|
| From setup to the pull request into the default branch | 66 minutes | 25 minutes |
| Time to merge each issue | 6 to 20 minutes | 4 to 5 minutes |
| Full test suite runs | 18 | 8 |
| Reviewer follow-up issues | 6 | 1 |

On 2.2.0, the full suite ran once per issue at merge, once for the drain, once in a test writer's session and twice in end-of-loop pass sessions. The 2.1.2 run shared the computer with other heavy work, so part of the time difference comes from that load; the run counts and follow-up counts do not depend on it.

Not proven yet: the release has not run on a large project or with Claude in every role. Test writer and end-of-loop pass sessions can still run the full suite themselves.
