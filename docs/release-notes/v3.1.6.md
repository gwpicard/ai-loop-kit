# v3.1.6

This release removes several causes of the parks and lost session time that stalled unattended runs. A changed test is now found before review, merge test failures go back to the builder with the failing tests, a builder that finished its work is no longer lost at the session limit, and the guard closes routes by which sessions ran the full suite or a recursive delete.

Most changes apply to every project, with Claude and Codex alike. Some have narrower reach:

- The priority change in item 6 applies only on macOS.
- The time budget for targeted runs in item 5 applies only to projects with a `Test files command`. So does the guard's refusal of the full Test command in item 7.
- Item 10 applies whenever `loop.json` on the loop branch differs from the checkout's, typically because a merged piece changed it.

## Updating

1. In Claude Code, refresh the marketplace, then update the plugin:

       /plugin marketplace update ai-loop-kit
       /plugin update ai-loop-kit@ai-loop-kit

2. Start a new Claude Code session so that the new plugin loads.
3. In the commands below, `<plugin>` is the installed plugin folder, the one that holds `bin/`. A loop that is already running keeps the version it started with. To move it to 3.1.6, stop it from the project root, wait until `.loop/loop.pid` is gone, and start it again:

       <plugin>/bin/loop stop
       mkdir -p .loop && nohup <plugin>/bin/loop run > .loop/loop.out 2>&1 &

This release needs no setup run and adds no setting to `loop.json`. Settings, labels, parked issues, the loop branch and its pull requests carry over unchanged.

While the loop branch's `loop.json` differs from the checkout's, the loop now uses the loop branch's file, so an edit to `loop.json` in the checkout does not reach a running loop until the loop branch carries it. `loop.local.json` still applies on top.

## What changes

1. **A changed test is found before review, not at merge.** When a builder or fix session's tests pass, or its targeted run times out, the loop now runs the merge's check for locked tests, existing tests and protected paths before the reviewer starts. A breach becomes the builder's next round, with the path and an instruction to revert the change or, if the issue needs it, to park and name the path.

   If the breach remains after the last round, the issue parks before review with a question that names the path, such as "May the builder change tests/test_feature.py?", so that a plain yes can grant a test file.

   On 27 November, in a field Swift app, an issue changed an existing test file. The loop ran a review, a fix round and a second review before the merge refused it, and its park named no path. Thirteen of the 15 waiting ready issues depended on it, and once the rest of the queue was done the loop had nothing to build for almost eight hours.

   On a case-insensitive file system, a locked test written with different letter case from the name Git tracks is now checked as well.

2. **An agreeing reply can grant the recommended test path.** When a park's question asks about a test change but names no test path, and its `Recommended:` line names exactly one, a reply such as "yes, as recommended" now grants that path. The grant comment says that the path came from the recommendation. When the recommendation names several paths, nothing is granted. An agreeing reply to a test-change park that grants no path now gets one comment that says so and asks for the paths.

   On 24 November, in the same project, "yes, as recommended" on one such park granted nothing and posted no notice. The issue parked again on the same question while 15 of the 19 remaining ready issues depended on it. That park also had a second cause, a note on the issue's allowed-path line, which this release does not fix.

3. **Merge test failures go back to the builder with the failing tests.** When the merge's Test command fails, targeted or full, the loop now reruns only the failing test modules that exist on the loop branch, with the Test files command. It runs the full Test command there only when it cannot name the modules or the `Test files command` is unset or lacks `{files}`. Before, only a failed full-suite run at merge was rerun on the loop branch, and always in full.

   When the failures are the issue's own, the builder gets a fix round with every failing line, the stack dump of any hung test, the log path `.loop/logs/<issue>-merge.log` and, when the Test files command takes `{files}`, the command that reruns just those modules. Failures that the loop branch shares are listed separately as not the builder's to fix. When no failure can be isolated to the issue, it parks as before.

   Each issue gets two of these merge test fix rounds, counted separately from `Max rounds`, so a build approved in its last review round can still be fixed. After two that still fail, it parks with the failing tests of the last attempt.

   On 26 and 27 November, in a second field project, five approved merges were refused on the full suite. Each refusal reran the whole suite on the loop branch, about 45 minutes in all, and the refusals with their fix and review rounds took about 2.7 hours of a 14-hour run. In this repository on 23 November, about eight merge parks in one day each needed an investigation by hand.

4. **A builder that reported its work is not lost at the session limit.** A builder session that times out after it has written its `BUILT:` report, with commits since it started and a clean working tree, now goes on to the loop's tests step and review instead of counting as a crash. The build log records `builder session timed out after BUILT; continuing with tests and review`. A session that times out without a report, or with uncommitted changes, still counts as timed out.

   The Stop hook now limits each command to the time the session has left, including any wait for memory or disk, and allows the stop when that time runs out.

   On 24 and 25 November, in the Swift app, every one of the 16 builder and conflicts sessions that reached the 60-minute limit had already written its `BUILT:` report. In one, the focused tests passed 18 minutes before the session was killed inside a Stop hook test run.

5. **A targeted run that outlasts its budget is reported once, not started again.** With a `Test files command` set, `loop check`, the Stop hook and the loop's tests step stop the Test files command after one third of `Session minutes`, and never before ten minutes. They report the budget and the number of files and warn that the project's Test files command may be running more than the named files.

   At the same commit in the same build, none of them starts the command again. The Check command is skipped, the Stop hook allows the stop and the build goes on to review. The loop records a `targeted-timeout` event and a line in `loop.out`, and tells the reviewer that the targeted run timed out. The merge still runs its tests as before.

   In the Swift app, the project's Test files command fell back to the whole suite for test files in a folder it did not recognise. Targeted runs became full ones, and nothing in the kit's output showed it until a builder found the cause about nine and a half hours into the run.

6. **On macOS, tests started inside a session no longer run at background priority.** Agent sessions now start with a raised niceness (`os.nice(10)`) instead of `taskpolicy -b`. Sessions still run at lower priority than the supervisor, but the Test and Check commands that `loop check` and the Stop hook start are no longer in the macOS background class. Other systems already used `os.nice(10)` and see no change.

   On 23 November, four test files of the second field project took 53 to 58 seconds at normal priority and 208 seconds under the background policy. On 26 November a 40-module `loop check` took about 19 minutes in a session, while the merge ran all 2,841 tests in about 9 minutes.

7. **The guard closes more routes to the full suite and to refused commands.**
   - The guard now reads code passed to `python`, `python3`, `node`, `sh`, `bash` or `zsh` by `-c`, `-e`, a heredoc or a here-string, including behind `uv run` or `env`. In every session it refuses a recursive delete written there, including the list form `['rm', '-rf', path]`. In loop sessions it also refuses the git and `gh` commands those sessions may not run and, in builder, test-writer, reviewer and pass sessions, the full Test command, written as one string or as a list of its words.
   - In loop sessions, the guard also reads a script before the session runs it as `bash <path>`, `sh <path>`, `zsh <path>`, `python3 <path>`, `python <path>`, `node <path>` or `./<path>`, when the script is untracked, changed since the session started or outside the project. It refuses the run when the script holds a recursive delete, a git push or merge, or, under the same conditions as in the first point, the full Test command. The refusal names the script. A tracked script the session has not changed runs as before.
   - When a builder prompt carries the person's replies, it now adds that a reply cannot widen the session's tests: the builder runs `loop check` and records any request for the full suite under DEVIATIONS, because the merge runs it. The builder instructions say the same, and also that a refused command is never moved into a script, interpreter code or project code, and that a builder whose issue needs the refused outcome parks.

   On 26 November, in the second field project, a reply asked a builder to run the full suite. Two 90-minute sessions ran it through Python's `subprocess.Popen` in a heredoc, and the issue parked after three hours while the next issue waited. The same night, in a third field project, a builder whose recursive `rm` was refused wrote the delete into a project script as `find -delete`.

   For Codex, the guard now reads interpreter code in a command given as a list of arguments, as it does for Claude. The builder instructions also tell a script that needs scratch space to create it under the system temporary folder and leave it there.

   The guard still cannot see a command assembled at run time, code in a file generated or fetched at run time, or code that a test or a project script runs.

8. **A retry after a merge refusal goes straight to the merge when nothing changed.** When an issue parked because the merge refused it, and its branch is still the commit that the last review approved, a reply now starts no test writer, builder or reviewer session. The loop catches the branch up with the loop branch and merges it with that approval. If the catch-up conflicts, the conflicts step runs as before. The build note says that the merge was retried using the last approving review.

   On 24 and 25 November, in the second field project, each retried issue of this kind ran a new builder session and review. Most took 4 to 14 minutes each; four took over an hour each, because their new builder sessions hit the `loop check` timeout.

9. **A pass that runs out of time names the command.** When a command inside the end-of-loop pass runs out of time, `pass.json` and the pass section of the final pull request now name the command, its text, its limit and the elapsed seconds, instead of "worker ended with exit code -9 and no result". `loop.out` now records the end of every pass, as `end-of-loop pass finished (N sessions)` or `end-of-loop pass failed:` with the reason.

   On 27 November, in the Swift app, the pass was killed after 30 minutes with no reason recorded and no end line in `loop.out`, and the morning session told the person that the pass "may be stuck".

10. **Settings changed on the loop branch apply for the rest of the run.** When `loop.json` on the loop branch differs from the checkout's, the loop now uses the loop branch's file for builds it starts afterwards, merges, the drain and the end-of-loop pass. `loop.local.json` from the checkout still applies on top, and `Loop branch` always comes from the checkout. `loop.out` records the change once, for example `settings: using loop.json from origin/loop/main, which differs from the checkout`.

    A loop branch file that fails validation leaves the checkout's settings in use, with one line naming the error.

    On 26 November, in the third field project, a piece extended the Check command and added a Smoke command on the loop branch. The next piece merged 50 minutes later without those checks, and the pass reported Smoke as `not set`.

11. **A reverted issue that is reopened is built again.** When an issue's pull request into the loop branch merged before the issue's latest reopening, the loop no longer closes it as already merged. It builds the issue from the current loop branch on a new branch, `issue/<n>-reopened-` followed by the reopening time, without a force-push, and only the tests locked since the reopening apply. A crash after a merge, with no reopening, is still completed and closed as before. Until now, rebuilding a reverted issue in this repository meant filing it again.

12. **A drain that overlaps the final merge no longer fails.** Before it creates the final pull request, the drain now fetches the default branch again. When the loop branch holds nothing new, it creates no pull request, writes `drained: nothing to merge` to `loop.out` and records a passing drain. A refusal from GitHub that there are no commits between the branches is treated the same way.

13. **A session's clean-up tolerates command lines that are not UTF-8.** When the loop lists processes to end a session, it no longer fails on another program whose command line is not valid UTF-8.

## What was tested

All 1384 tests in the kit's suite pass in a fresh single-branch clone with the default temporary folder, and the loop's own full run of the Test command on the loop branch passed. New tests cover each item above, including each guard form for Claude and Codex, a builder that reports `BUILT:` then hangs, for Claude and Codex, a Test files command that sleeps past a short budget, a merge failure isolated to the issue and one shared with the loop branch, and a default branch that gains the loop branch's commits while the drain's tests run.

The kit's own test helpers that list processes now replace bytes that are not valid UTF-8. On 27 November one kit test errored during a merge's rerun on the loop branch because another process on the machine had such a command line. This changes no behaviour in a project.

Not proven yet: none of these changes has run in a field project. The kit's own loop built them while it ran 3.1.5, so none has run in an unattended loop either, and the effect of the priority change on session test times has not been measured.
