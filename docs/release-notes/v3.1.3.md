# v3.1.3

This release stops builder sessions from spending their time on the full test suite. A session now runs only the issue's targeted tests and leaves the full suite to the merge, and the Stop hook no longer repeats a `loop check` that has already passed. The release also closes gaps in the guard and keeps the real reason when a build's clean-up fails after a timeout.

The targeted selection in item 1 applies to projects with a `Test files command`. The Stop hook change in item 2 applies to every project.

## Updating

1. In Claude Code, refresh the marketplace, then update the plugin:

       /plugin marketplace update ai-loop-kit
       /plugin update ai-loop-kit@ai-loop-kit

2. Start a new Claude Code session so that the new plugin loads.
3. In the commands below, `<plugin>` is the installed plugin folder, the one that holds `bin/`. A loop that is already running keeps the version it started with. To move it to 3.1.3, stop it from the project root, wait until `.loop/loop.pid` is gone, and start it again:

       <plugin>/bin/loop stop
       mkdir -p .loop && nohup <plugin>/bin/loop run > .loop/loop.out 2>&1 &

This release needs no setup run and adds no setting. Settings, labels, parked issues, the loop branch and its pull requests carry over unchanged.

## What changes

1. **Builder sessions run only targeted tests.** With a `Test files command` set, `loop check` and the Stop hook no longer fall back to the full Test command when the selection exceeds 40 test modules. They run the locked test files and the test files the branch changes, then add tests that import the changed code, in selection order, up to the cap. When the locked and changed files alone exceed the cap, they run them all. The line that names the selection adds `merge runs the full suite`. Over the cap, the merge still runs the full Test command.

   The builder instructions now say that a session runs only targeted tests, that the merge runs the full suite, and that a builder never parks to ask for a longer test limit or a wider test scope.

   On 24 and 25 November, in a field project on 3.1.2, five issues spent about 7.9 of 11 hours of run time in builder sessions whose `loop check` selected the full suite (163 to 265 modules) and timed out at 30 minutes, after covering 20 to 65 per cent of it. Both parks and the one crash of that run followed such a timeout, and one builder parked to ask for a longer test limit. The merge ran the same suite in 9 to 13 minutes.
2. **The Stop hook does not repeat a passing `loop check`.** When `loop check` passes with a clean working tree, it records the commit, the selection inputs and the settings in the build's temporary folder. The Stop hook reuses that result when all of them still match, and runs nothing. A new commit or an uncommitted change means it runs its commands again.

   The same night, in a second field project on 3.1.2, 16 builder and conflicts sessions reached the 60-minute session limit: 960 of about 1,120 session minutes, or 86 per cent. Every one had already written its `BUILT:` report. In the sessions examined, the suite ran twice: once from the builder's `loop check` and again from the Stop hook.

   In that project, the full suite ran partly because the selection exceeded the cap and partly because the project's own test script ran the whole suite for a path it did not recognise. This release addresses the first cause and the repeated run, not the second.
3. **The guard checks quoted and prefixed command forms.**
   - `git -C "my dir" push` and `git -C 'my dir' push`, with a quoted folder name, are judged like any other push.
   - In loop sessions, `gh` reached through a path is refused when `env`, `sudo` or a `VAR=value` assignment comes before it.
   - The commands inside `$(...)` or backticks in the body of an unquoted heredoc are checked as commands. A quoted heredoc, such as `<<'EOF'`, stays data.
   - Every file named to `tee`, and every quoted redirect target, including one with a space, is checked against the locked and existing tests.

   When the guard cannot load its own modules inside a loop session, it now refuses the call with the rule `guard-error`. Outside the loop it still allows the call and writes `guard: cannot load, allowing the call:` with the error to standard error.
4. **A failed clean-up after a timeout no longer hides the timeout.** When the build's temporary folder cannot be removed, the loop writes `could not remove build temporary folder` with the folder and the error to `loop.out`, leaves the folder in place and carries on.

   A builder session that timed out is reported as `builder session timed out after` its limit in minutes, in the event and on the issue, rather than as the `OSError` from the clean-up. A process that outlives the session can also no longer recreate the process-group file while the folder is being removed.

   On 25 November, in the second field project, two builds crashed with `Directory not empty` and `Resource busy` after sessions that had in fact timed out, and one park asked the person to read logs about the folder rather than the timeout. Disk images that a project's tests leave mounted in the folder are not detached by this release; the folder now stays in place instead.
5. **Dependent issues can start in the cycle their dependency merges.** When a build merges, the loop now counts its issue as closed at once, so an issue that depends on it can start in the same cycle rather than wait for the next list of issues from GitHub.

## What was tested

All 1242 tests in the kit's suite pass on macOS, run from a fresh worktree. New tests check a session selection over the cap, with 45 importing tests and with locked and changed tests alone over it, a merge over the cap that still runs the full suite, a Stop hook that runs nothing after a passing `loop check` and runs again after a new commit or an uncommitted change, each quoted and prefixed command form in item 3, a guard that cannot load with and without a loop role, a clean-up that cannot remove an entry, and a timed-out builder whose folder remains.

Two tests that passed or failed with machine speed, and each failed one CI run of the 3.1.1 release pull request, now wait for the events they check instead of comparing times. A test of temporary-folder layouts that ran the whole flow module twice, and took as long as the rest of the suite, now runs only the three flow tests that check worktree paths, with a time limit on each run, and removes its folders even when a run fails or is killed. The kit's test runner no longer passes the enclosing session's loop role to the tests.

Not proven yet: none of these changes has run in an unattended loop, because the loop that built them ran 3.1.2.
