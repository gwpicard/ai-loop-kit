# v3.1.1

This release addresses several causes of stalled or parked work in an unattended run: test runs no longer inherit the background priority of agent sessions, targeted merges run the tests that import the changed code, a failed merge keeps the test output, the end-of-loop pass runs beside builds, and the loop restores its branch when it is missing on GitHub. It also recognises more test file names, parks an issue whose pushed commits a session rewrote, adds a setting that lets Codex sessions reach the network, improves setup's migration, and shows work left from an earlier run.

Most changes apply to every project. The following depend on the project or the operating system:

- In 3.1.0 the whole loop ran at background priority, and the Test command inherited it. On macOS, background work runs on the efficiency cores only, so the full suite at merge ran several times slower and could reach the fixed 30-minute limit. In 3.1.1 only agent sessions run at background priority; the Test command runs at normal priority, and its limit is a new setting, `Test minutes`. On macOS the sessions start under `taskpolicy -b`; on other systems the session process raises its nice value by 10 instead, and the loop itself no longer does.
- A project with a `Test files command` that contains `{files}` now has its targeted merges and `loop check` also run the test modules that import a changed Python module, or, for other languages, the test files that mention the changed file's name. Without such a command, every merge still runs the full Test command.
- In a project whose test files are named like `EditorTests.swift`, `FooSpec.scala`, `FooSpec.hs`, `foo_tests.rs`, `login-test.js` or `TestFoo.java`, the kit now treats those files as tests. In 3.1.0 a test writer could not name such a file, so its issue would park before reaching a builder. Existing files with these names are now also locked against builder edits, like any other existing test.
- A repository with "Automatically delete head branches" turned on now gets a warning from setup and at loop start.
- A project that still has a `PLAN.md` or a `## Loop` section in `AGENTS.md` gets the setup changes in item 9 when it runs setup to migrate.
- A project whose builds use Codex gets the network setting and the sandbox check in item 13.
- In a project without its own commit-msg hook, squash commits no longer carry session links or generated-by footers into the loop branch.

## Updating

1. In Claude Code, refresh the marketplace, then update the plugin:

       /plugin marketplace update ai-loop-kit
       /plugin update ai-loop-kit@ai-loop-kit

2. Start a new Claude Code session so that the new plugin loads.
3. In the commands below, `<plugin>` is the installed plugin folder, the one that holds `bin/`. A loop that is already running keeps the version it started with, including its priority. To move it to 3.1.1, stop it from the project root, wait until `.loop/loop.pid` is gone, and start it again:

       <plugin>/bin/loop stop
       mkdir -p .loop && nohup <plugin>/bin/loop run > .loop/loop.out 2>&1 &

This release needs no setup run. Settings, labels, parked issues, the loop branch and its pull requests carry over unchanged.

The new optional `loop.json` setting `Test minutes` sets the time limit of the Test command, in whole minutes of at least one. It defaults to 30, the limit 3.1.0 used. If your full suite can take longer than half an hour at merge, raise `Test minutes` before you restart, for example:

    "Test minutes": 60

If your builds use Codex and your Prepare command fetches packages, set `"Codex network": true`.

If your repository has "Automatically delete head branches" turned on, turn it off in the repository's Settings, General, Pull Requests. Otherwise, merging the loop's final pull request deletes the loop branch. The loop now restores the branch, as item 6 describes, but turning the setting off avoids the deletion in the first place.

## What changes

1. **Agent sessions run at background priority; tests run at normal priority.** The loop process no longer enters the background class. Instead, it starts every Claude and Codex session, including the pass and summary sessions, under `taskpolicy -b` on macOS when `taskpolicy` is available, and otherwise lowers the session process's priority with a nice value of 10. Commands that a session starts inherit its priority. The Test, Check, Prepare and Smoke commands that the loop itself runs, including the full suite at merge and at the drain, run at normal priority.

   In a field project on 22 and 23 November, a suite that takes 8 minutes at normal priority reached the 30-minute limit at every merge under 3.1.0, and the timeouts caused eleven parks overnight.

   The new `Test minutes` setting sets the Test command's time limit at merge, at the drain and in targeted checks; the Prepare, Check and Smoke commands keep their 30-minute limit. When the Test command times out at merge or at the drain, the refusal now names the limit, the elapsed time excluding pauses and the setting that controls it, followed by up to 60 lines from the end of the command's output.
2. **Targeted merges run the tests that import the changed code.** With a `Test files command` set, a merge that runs targeted tests, `loop check` and the builder's Stop hook now add to the locked and changed test files every test module that imports a changed Python module, whether directly, through a `from` or relative import, or through a package initialiser. It also adds the test modules that import a changed test helper or fake, or a test module already selected.

   Imports are read by parsing the files; no project code runs. For other languages, or a file that does not parse as Python, a test file that mentions the changed file's name without its extension is selected.

   When the selection exceeds 40 test modules, the merge or check runs the full Test command instead. The merge's line in `loop.out` and the build note list each added module and the import or mention that selected it. On 22 and 23 November, two regressions in the kit reached the loop branch because the merge ran only the changed test files, and were found only at the next full run.
3. **A failed merge keeps its test output.** The merge now writes the full output of its Prepare, Test and Check commands to `.loop/logs/<issue>-merge.log`, replaced on each attempt. When a due full suite fails and the loop runs it again on the loop branch, that run's output goes to `.loop/logs/<issue>-merge-baseline.log`.

   The refusal, which goes to the builder or appears in the park, keeps its first line and adds the log's path and up to 20 failing lines: those starting with `FAIL:` or `ERROR:`, or a module summary that reports failures. When it finds none, it quotes the last four lines instead. When both branches fail and the failing tests can be identified in both outputs, the park also says whether the same tests fail on both branches. On 23 November, finding the cause of a run of merge parks took two extra full runs by hand because nothing recorded which tests had failed.
4. **The loop stops after the same error repeats, but not on a GitHub outage.** When an exception of the same type and message ends three cycles in a row, the loop writes `stopped after 3 identical failed cycles:` with the error to `loop.out`, followed by the traceback, records a `crash` event with the traceback, writes the reason on the Factory board and exits with a non-zero status. A different error, or a cycle that succeeds, starts the count again. Before this change, such an error repeated every cycle until someone noticed.

   A GitHub error, or an operating-system error such as a failed network connection, never counts towards the stop: the loop says it will check again, waits its usual interval and tries again for as long as the outage lasts, as in 3.1.0. The board write itself no longer fails when the Factory issue cannot be found on GitHub.
5. **The end-of-loop pass runs beside builds.** In 3.1.0 the drain ran the pass itself, and no build started and no reply to a park was read until it finished; on 21 November each pass took 18 to 37 minutes. The drain still runs the full Test command first. It then starts the pass in a worker process on a fixed commit of the loop branch and returns to its cycle, so replies are read and builds start while the pass works. Only one pass runs at a time. The pass takes a slot of its own, so even with `Parallel` set to 1, a build can run beside it.

   When the pass ends, the loop updates the final pull request with its report, which now names the commit the pass ran on. If the loop branch has moved on meanwhile, the next drain runs a new pass on the newer head. The same worker writes the pull request's Summary, Evidence and Merge danger sections; until it finishes, the body says `The summary is pending.`, and `The summary did not run.` appears only when that step failed.

   A pass that crashes leaves an error in the pull request body and does not stop the loop. `loop stop` waits for a running pass as it waits for builds, and `loop stop --now` ends it. The worker's output goes to `.loop/logs/pass-worker.log`.
6. **The loop restores its branch when it is missing on GitHub.** At the start of each cycle, and before it merges an issue, the loop checks that the loop branch exists on origin. When it does not, the loop pushes it again at the last commit it knew, or at the default branch when that commit is unavailable. It writes `restored <branch> from <source> at <commit>` to `loop.out` and records a `loop-branch-restored` event. On 22 November, merging the final pull request deleted the loop branch; the next issue's merge then failed and parked, and about two hours were lost.
7. **Setup and the loop warn about automatic branch deletion.** When the repository has "Automatically delete head branches" turned on, setup prints this line, and the loop prints it once when it starts:

       warning: in Settings, General, Pull Requests, turn off "Automatically delete head branches": merging the final pull request deletes the loop branch.

   The check makes one GitHub call with a two-second limit. When the setting is off or cannot be read, or the check fails in any way, nothing is printed and setup and the loop carry on. `kit/README.md` gives the same advice under "Set up a project".
8. **More test file names are recognised.** The kit now treats these names as tests, in any folder: `*_tests.*` and `*-test.*`, such as `foo_tests.rs` and `login-test.js`; `*Tests.swift` and `*Test.swift`; `*Spec.scala` and `*Spec.hs`; and Java files whose name starts with `Test`, such as `TestFoo.java`. The class-style names are case-sensitive, so `Contest.swift` and `Respect.scala` stay source files. A test writer can now name such a file in its `TESTS:` block, and the guard and the merge check lock an existing one as they lock an existing `test_*.py`. On 22 November kit 3.1.0 rejected `marcdownTests/EditorTests.swift` in a macOS project, so every issue in that project would have parked at the test writer step.
9. **Setup migrates the whole plan and says what is left.** When the loop branch on origin holds a `PLAN.md`, setup now files the inbox issue from that version rather than from the checkout, since the newest entries stay on the loop branch until its final pull request merges. It prints `PLAN.md: read from` and the branch it used. In a field test on 22 November, the checkout's `PLAN.md` had 108 lines and the loop branch's 199.

   After a migration, setup ends with `next:` lines, in order: place the contents of `PLAN.md` using the inbox issue it names; commit `loop.json`, `AGENTS.md` and `.gitignore` through a pull request; update the checkout once it merges; and merge the default branch into the loop branch before restarting the loop.

   Setup also adds a `next:` line quoting each line of `AGENTS.md` or `CLAUDE.md` that still names `PLAN.md`, warns when `AGENTS.md` has uncommitted changes that the migration uses, and names a dropped `Builder model` or `Reviewer model` setting. The setup skill relays these lines and does not start the loop until you have seen them.
10. **Work left from an earlier run is shown after a restart.** `loop status` now ends with an `Open parks` section that lists every open issue labelled `needs-user` with its latest park question, whatever the time window. It reads them from GitHub and says the section is unavailable when GitHub cannot be read; `loop status --json` is unchanged.

    The Factory board now lists an open pull request from the loop branch into the default branch from the first cycle after a start, rather than from the next drain. The loop skill tells the session, after it starts the loop, to tell you which parks and which final pull request need you.
11. **A resumed build keeps unpushed commits.** In 3.1.0 a build that started again reset the issue branch to its copy on GitHub, which dropped any commits made before the first push. Now, when the local branch holds commits that the remote branch lacks and the two have not diverged, the build starts from the local branch and pushes it first. When they have diverged, the loop keeps the local branch under a backup name beginning `issue/<issue>-local-`, writes `kept divergent local branch as` and that name to `loop.out`, and starts from the remote branch as before.

    A build that parks now pushes its branch first when it holds commits. On 22 November, five parked issues in another project held 2 to 10 unpushed commits each.
12. **A reply to a park says whether it granted a test change.** The rule is unchanged: a yes grants the test paths named in the park's question only when the last reply holds no doubt word. The loop now reports the outcome on the issue:
    - When a reply grants paths, the loop comments `Added to ## Protected paths this issue may change:` followed by the paths.
    - When the last reply starts with a yes but holds a doubt word such as `only` or `but`, the loop comments that the paths were not granted, names the doubt word, and says that a plain `Yes.` as the last reply grants the named test paths that the stops list permits. The issue still returns to the queue with the reply, as before.
    - When a park question mentions a test, fixture or lock but names no test path, the park comment adds `No test path was named in the question, so a yes cannot grant one.`

    The session instructions now tell sessions to name the path of any test file that a park asks to change. On 22 November, replies that granted nothing silently caused four extra parks across three issues.
13. **Codex sessions can reach the network, and a sandbox that refuses tests stops the loop at start.** A new optional `loop.json` setting, `Codex network` (default `false`), gives Codex sessions network access inside their sandbox when true, so a fresh worktree can fetch packages. The setup skill proposes it for projects whose Prepare command fetches packages. When any role uses Codex, the loop runs the Test files command on one test file inside the Codex sandbox at start, or the Test command when no Test files command is set; if the sandbox refuses it, the loop stops with a message that names the sandbox rather than parking issue after issue. When a Codex reviewer reports that the sandbox refused its command, the issue parks with a message that names the sandbox, instead of using up its review rounds or sending the refusal to the builder as a fix.
14. **A session cannot rewrite pushed commits unnoticed.** Before it pushes an issue branch, the loop checks that the local branch contains the remote one. When a session has rewritten pushed history, the issue parks with a message that says so and names the commits the remote has and the local branch lacks; the loop never force-pushes. Errors from git and gh now keep up to the last 20 lines of their error output, so a rejected push shows git's reason.

    The reviewer brief now explains that the loop squash-merges the issue branch and applies the project's sign-off and attribution settings to the squash commit, and tells the reviewer not to ask for commit-message or sign-off changes on the issue branch. The session instructions say never to rewrite, amend or rebase commits that are on the remote. On 22 November, a session in a field project rewrote three pushed commit messages, and the issue parked with only "Read .loop/logs".
15. **`loop.out` records each issue's progress.** The loop now writes one line to `loop.out` for each requeue on a reply, review verdict, merge and park, in the form `#<issue> review: APPROVE` or `#<issue> merged`. A requeue on a reply also records an `answered` event in `.loop/events.jsonl`. In a field run on 22 November, `loop.out` held three lines after two requeues, two reviews and a merge, and the session reported the merged issue as still building. The loop also now appends to `loop.out` when it was started with `>`, so its own lines no longer overwrite lines that build processes write to the same file.
16. **Smaller changes.**
    - When the loop squashes an issue's commits, it now removes session trailers, lines holding a session link, lines other than co-author lines that hold the agent vendor's no-reply address, and generated-by footers, with or without their link. Matching ignores case, and ordinary prose that names the agent stays. The filter applies whatever `Agent attribution` holds; that setting still decides only whether agent co-author lines are kept.
    - A test writer can keep editing a test file it created in the same session. In 3.1.0 the guard refused such an edit, as `test-lock`, once the file was staged or committed. The guard now judges a test writer's edits against the session's start commit, as it already did for the builder. A test file present at the start commit is still refused with `test-lock`.

## What was tested

All 1201 tests in the kit's suite pass on macOS and Linux. Each change comes with new tests, among them session commands wrapped by a fake `taskpolicy` while test commands are not, a Test command that prints and then hangs past `Test minutes`, test selection replayed against the two regressions in item 2, failing fake commands for the merge logs, a cycle that raises the same error three times and a GitHub error that repeats ten times without stopping the loop, a fake long pass during which a build starts, a deleted loop branch on a fixture remote, a parked build with a local-only commit, a rewritten pushed commit, a fake Codex sandbox that refuses the tests, and each newly recognised test file name.

The kit's own test runner now records the stack of every thread in a test process that passes its time limit and reports the process as hung. Three tests that failed only when the loop ran them, because their fixture path contained `.loop-worktrees`, now check the worktree folder itself. Tests that failed only on the Linux runner, because they read an unset `TMPDIR` or assumed the macOS `/bin/sh`, have been fixed. A new house rule refuses test code that reads `TMPDIR` directly or calls a macOS-only tool without a platform check, and four further tests that read `TMPDIR` now use the system's temporary folder.

Not proven yet: none of these changes has run in an unattended loop, because the loop that built them ran the released 3.1.0. The timing figures in item 1 were measured under 3.1.0, not with this release. The branch restoration and the deletion warning have been tested only against a fake GitHub.
