# Answers to the design document's open questions

Design document: https://claude.ai/artifact/FZwf7EWnuG5ZH94RyW7XCF
Answers from the maintainer, 5 October 2026, gone through one by one in chat.

1. Where v1 lives: here, in gwpicard/ai-loop-kit, which is already a new repository. AI Build Kit's files in it are removed gracefully and carefully, and replaced entirely by the loop kit. A removal plan is needed (what to borrow first, what to delete, in what order, without breaking anything mid-way).
2. Integration: all of a run's pieces are combined on one run branch, because all changes are expected to work together, and the relevant checks run on the combined result. A separate (isolated) pull request for one piece is created only when that piece needs individual review. Follow-ons: approval applies to the run's pull request or an isolated piece's own; finding the culprit in a red combined result (question 17) is needed in v1; the run loop gains a join-and-check step.
3. Auto-approve: never automatic by default. A merge without the person happens only when they specifically approved it before that run started (per run, not a standing setting). Proposed and not objected to: even when pre-approved, the merge still needs green checks on the up-to-date combined branch, every judge passing with an unchanged bar, a clean fresh review, and no piece with a must-look reason; otherwise it waits for the person.
4. Research staleness: fingerprint plus age, and always a quick check at build time. Every finding records its source, date and what it rests on (an in-project file and fingerprint, or an outside page or package version). At every claim the run does a quick check of every finding: fingerprints for in-project ones, version and age for outside ones. A smart escalation decides when a fuller refresh is needed (fingerprint changed, version changed, past the age limit, or the quick check disagrees): the run re-researches that finding, and only a finding it cannot confirm, or one whose new answer changes the spec, sends the piece back to shaping.
5. Budgets: no limit on a run (it depends on how many pieces it has). Per piece: 3 attempts, or earlier when attempts stop making substantial improvement (for example a goal metric that no longer moves). No time limit on a piece, because a piece can take time for good reasons; only a piece that is clearly stuck is stopped. Proposed meaning of "clearly stuck": no progress signal (no new commit, no new judge result, no change in output) for a set time, or the same failure repeating; the watchdog reads this from the run's heartbeat.
6. "needs-you" is also a label: a flag the gate adds when a piece's computed needs include something only the person can answer, and removes when none are left. Not a state; the person never sets it.
7. Commands: /setup (the project, and deployment through a recipe, in one guided flow; run again to add or change deployment, as AI Build Kit's setup and /ship did), /shape (capture an idea, or shape one until ready), /run (build, review and combine ready pieces; open the pull request), /maintain (core: find drift between records and reality, code health decay, tidy leftovers, turn lessons into checks, update the kit; findings become new issues in shaping), /what-now (what is where, what needs the person, run progress, what was decided alone; not /status, which Claude Code already uses). No /approve: merging is merging the pull request on GitHub or telling the agent to merge; closing it or commenting a reason sends pieces back. No separate capture or fix command.
8. Claude Code only for v1.0. The gate script and spec checks stay plain scripts any agent or person can run, so Codex can be added later as an extension.
9. Safety: the essential level is core in v1.0 (deny rules for push to main, force push, recursive delete and hand-written state labels; no reads of real env files and throwaway values in each worktree; a secret scan before every push; a yes before anything posted in the person's name; text from issues and the web treated as data; a new-dependency age and licence check). The full sandbox with a network allowlist and a scoped token held by the gate comes later.
   Design principle added by the maintainer: prefer deterministic checks and blocks over written instructions wherever possible, with redundancy. Examples: deny and ask rules in Claude Code settings, hooks that refuse commands, tokens whose scopes cannot perform certain actions, git hooks, the gate refusing moves, and server-side GitHub settings. Where a rule matters, hold it in at least two independent layers (for example a settings deny rule and a hook, or a hook and a GitHub branch rule), so one failing does not open it.
10. Records model: one home per fact. A short AGENTS.md as an index (about 150 lines at most); a short project overview (what it is, who it is for, the product's areas and the sensitive ones); the area map with a check that every folder belongs to an area; decisions and behaviour live on the pieces, and each piece's behaviour change is applied to the overview or docs in the same pull request as its merge; the changelog written from merged pieces; /maintain checks it all for drift.

## Follow-ups the maintainer asked for (not questions)
- Once the plan is final, research the records model (and the plan generally) against current best practice, to confirm it and make the best version of it.
- Later, a strict pass over the skills written for AI Build Kit, together with the key principles skills must follow to work as well as possible, before v1's skills are written.
11. Judge files: option A. Shaping cuts the piece's branch from main and commits the judge's test files as its first commit (the frozen bar, fingerprinted at ready). Every file related to the build lives on the piece's branch. At merge, the acceptance tests stay and become ordinary project tests that guard the behaviour; scratch files (attempt notes, the frozen spec copy, judge logs, the run's working state) are removed before merge so they never reach main and never cause conflicts. What must last is recorded in the issue or the changelog. A cheap judge (a measuring script) may stay as a regular check; an expensive one (a reference critic) is dropped. Merges carry code changes and logical document changes such as the README, not working files.
12. Risk acceptance: on the issue only. The spec's Sensitive areas section holds the risk notice, the person's exact words and the date; the ready gate refuses a sensitive piece without it; any overview line the acceptance makes untrue is updated in the same pull request as the piece's merge. No separate records pull request.
13. Shaping crews are in v1, as a core part of the kit's design: several researchers on different sources whose findings are then reconciled, and several prototypes built side by side for the person to choose from. Follow-ons: the computer-resource sizing that limits a run also limits a crew; a rule is needed for reconciling researchers who disagree (a disagreement becomes a need on the piece, settled by the person or by a further check).
14. Anti-gaming, essential in v1:
   - Guarded against change: the judge and everything it rests on (tests, measurement scripts, fixtures, references, test settings) are frozen at ready and checked byte for byte before a piece leaves building. Removing, skipping, loosening or retrying a test to pass counts as a failed attempt, never a pass.
   - A held-out check for measurement judges: shaping sets aside a second measurement the builder cannot read (held by a deny rule and a hook); the gate runs it when the builder claims the target; a hidden result much worse than the visible one is treated as gaming.
   - The maintainer's addition: a hypothesis list written before building. For metric pieces (and any piece where the route is open), shaping or the first build step writes the hypotheses that might improve the result, and they are fixed before any attempt. Each attempt names the hypothesis it tests and records the result, so the target and the means cannot be changed after the fact. A new hypothesis may be added only in the same direction as the goal, and the reason is recorded; anything outside the list or against the goal's direction is refused or sent back to shaping.
15. Outside critic: an available choice from v1. When a reference-match piece is shaped, the kit asks whether to use a critic from another vendor (Codex, if installed and signed in, with the person's agreement that content goes to that provider). If the person does not have it or declines, the critic is a fresh Claude session. The choice can be changed later in the policy file.
16. Trim pass: kept in v1 as the last step of the build loop, with its limits (remove or fold only, never tests, only code this piece added, its own commit, thrown away if any check fails afterwards). Follow-up: later, define specific, well-defined checks for it; the maintainer points to Matt Pocock's list of such checks (for example tautological tests) as a source to research.
17. In v1: the run joins pieces onto the combined branch one at a time in dependency order and runs the checks after each join; on red, the piece just joined is the suspect, confirmed by one re-check without it; it is taken out and sent back to building with the failure and the piece it clashed with written on it; the rest of the run carries on. A check that fails only on GitHub's machines is an environment failure: the piece goes back to ready with a note, never counted as an attempt.
18. Notifications: all six moments (run finished; run stopped on a real stop; pull request ready for merge; went live or a live check failed; something waited on the person too long, about 2 hours; the watchdog gave up), each sent once per event, with quiet hours in the policy file (except real stops and the watchdog giving up). Non-blocking by design: a notification never pauses the work. The system has channels for alert, feedback and input (notifications out; a mailbox and comments on the issue or pull request in), and the run carries on with everything that does not depend on the answer, picking up the person's input whenever it arrives and resuming the affected piece from there.
19. Live: in v1.0, a health check after each deploy of main (notify and open a bug issue on failure) and automatic rollback to the last good deployment, both part of the deploy recipe in /setup. Later: error reporting into issues (with grouping) and tracing or performance signals into issues, as the Live extension proper. The maintainer wants a solid plan for that later implementation, written as part of the design.

## Research findings (research/spec-driven.md, agentic-loops.md, gates-determinism.md), decided 5 October 2026
Folded in, all of them, except B4:
- A. The run is a plain script, not an agent. It starts each builder as a separate non-interactive Claude Code session (claude -p) that cannot ask questions; builders get one "needs the person" tool that parks the piece and returns at once.
- B1. Agents use their own fine-grained token for this repository only, unable to change settings or workflows; the person merges under their own account. Creating it is a one-time step for the person.
- B2. Guards guard themselves: deny rules and sandbox write-blocks on the gate, hooks, settings and workflows; a pre-run check refuses to start while a guard is missing.
- B3. The hook parses commands rather than matching text, and the filesystem sandbox moves into v1 (revises answer 9).
- B4. NOT adopted in full. No second check layer on GitHub per piece or per run. Instead, the final combined pieces are checked (locally) at the end of the run, and if anything fails, only the relevant pieces are rebuilt.
- B5. /setup detects a free private repository with no server-side rules and says so plainly.
- C. Anti-gaming: a sanctioned "the bar is wrong" outcome (back to shaping, no attempt counted); hidden held-out cases for acceptance tests too; a lint on new tests (no assertion, skipped, mocking the project's own code); a "must stay the same" field proved by checks that pass on main and join the frozen bar.
- D. Specs: IDs on flow steps and edge cases with tests naming the ID they prove; coverage categories answered or marked not applicable with a reason; two fresh sessions each list the tests they would write, differences become needs; edge cases in "When ..., then ..." form; a Limits field with numbers; a Follow line; question discipline (a cap per sitting, why it matters, a recommended answer, low-impact unknowns as recorded assumptions); a behaviour change record checked at merge; one shared spec parser and a versioned spec format; a quick path with lighter required fields for small changes.
- E. Mechanics: stuck means repeated patterns plus a hard timeout per test run; usage limits pause as "waiting for reset" without counting an attempt, tokens recorded per piece; each attempt starts fresh with a gate-kept attempt log and a fixed hand-off; each join re-runs the joined pieces' judges and checks declared touches against the diff; merge only the exact tested commit, one merging run at a time, the gate judges flakiness; the run pull request grouped by piece with evidence per piece, split when too large.
- F. Review and learning: every finding becomes a failing check or a shaping issue; the outside critic is advisory unless a check reproduces its finding (refines answer 15); lessons need evidence, become checks first, and are pruned; a hook logs every command; /maintain reports change-fail and rework rates.
- G. Supply chain: package managers' minimum-age setting and no install scripts; secret scan in two places; Dependabot; Actions pinned to exact versions.

## Micro loop 1, the shaping loop: agreed as revised with the research
- Questions for the person come in small batches with a cap per sitting, each with why it matters and a recommended answer; low-impact unknowns become recorded assumptions.
- The two fresh-session test lists run only once the cheaper lint passes.
- Quick path for a small change: one piece, one area, no sensitive area, no new dependency, a judge that is a single test.

## Micro loop 2, the build loop: agreed as proposed
- A fresh non-interactive builder session for every attempt, given only the frozen spec, the gate-kept attempt log and (for metrics) the next hypothesis; never past session history or held-out cases.
- Fixed hand-off outcomes: done, bar is wrong, needs the person, blocked by environment, gave up. The gate judges: frozen bar byte for byte (a change is a failed attempt logged as possible gaming), visible judge then hidden held-out cases, metric target and held-out twin, hypothesis from the list, new-test lint, must-stay-the-same checks, touches.
- Outcomes: pass leads to the trim pass then review; failures with attempts left retry; 3 attempts or no real improvement go back to shaping; bar is wrong goes to shaping without counting; needs the person parks the piece while the run continues, resuming in the same run if the answer comes, otherwise back to ready with the answer in the spec; environment failure goes back to ready; usage limit waits for reset; stuck (the same error 3 times in a row, or the same change undone and redone, or a test run past its hard timeout) stops the attempt and counts it.

## Micro loops 3 and 4, integration then review: agreed as proposed
- Integration: a combined branch cut from main at run start; each built piece joined in dependency order (combined branch brought up to date with main first, scratch files excluded, tests kept); after each join, every joined piece's judges (visible and held-out), must-stay-the-same checks and declared touches re-run; on red the just-joined piece is confirmed by one re-check without it, taken out and sent back to building with the clash written on it; a merge conflict is treated the same way and agents never resolve conflicts across pieces. A final combined check (full project checks, validator if any, every judge) runs locally after the last join; failures send only the relevant pieces back. Pieces needing individual review are not joined and follow the same steps on their own branch and pull request.
- Review: a fresh reviewer sees only the specs and the combined diff piece by piece. Every finding becomes a failing check (the piece returns to building), a shaping issue (the spec was wrong), or a worth-knowing note. A new test from a finding joins the frozen bar with a written justification for the person to review. Up to 2 review rounds, then a remaining finding parks that piece and the others go ahead. The outside critic, when chosen, is an advisory second reviewer and sends nothing back unless a check reproduces its finding. When clean, one pull request grouped by piece with each piece's evidence; pieces move to approval.

## Meta loop 1, the run: agreed as proposed
- A plain script started by /run. Pre-run check refuses to start, with the reason, unless every guard is in place (deny rules, hooks, sandbox, gate untouched, agent token), the policy file is readable, the computer's power, sleep, memory and disk are fine, and main is green. It asks two things once: which pieces, and whether the merge is pre-approved (default no).
- Loop: plan by dependency and area; claim as slots free up with the claim re-check; route each build outcome; at every step read the mailbox, write the heartbeat and run record, send notifications without waiting; final combined check, review, one pull request (plus isolated ones); merge only if pre-approved and every condition holds, else wait for the person's merge on GitHub; close with a morning summary, "run finished", and lessons to the learning loop. Resumes from the run record after a crash without redoing finished work.
- Parallel builders sized from free memory, capped at 3 by default in the policy file.
- An answer to a parked question that arrives after the run has ended waits for the next /run; the person is told the piece is back in ready with their answer, so they know something happened.

## Meta loops 2 to 5: agreed as proposed, with these values
- The watch: a system job on the computer (launchd on macOS), independent of any chat session, every 15 minutes while a run is going. Reads heartbeat and run record only; restarts a dead run script, stops stuck attempts, resumes after a usage reset, makes sure real stops were notified once; gives up after 3 failed restarts with a notification; logs every check and action.
- Learning: evidence collected at run end and on every kickback or finding; a pattern seen at least twice becomes a lesson candidate; lessons become checks first where possible. Cheap additions (for example a new lint pattern) may be added by decide-or-park and flagged for review; anything larger waits for the person's approval in /what-now. Stale lessons are offered for removal.
- /maintain: the kit suggests it every 2 weeks. Drift between records and code, code health (including mutation testing), delivery health (change-fail and rework rates), tidying, kit updates; findings become issues in shaping, small tidying is done directly and logged.
- Live feedback: in v1, a health check after each deploy of main, and on failure an automatic rollback, a bug issue in shaping and a notification. Later: errors and slow requests become grouped issues, with a written plan in the design.

## Final three, and the move 7 change (agreed)
- Move 7 (back to ready, spec untouched, no attempt counted) also starts from approval, and also covers a parked piece whose answer arrives after its run ended.
- Notification channel: a Claude Code push notification to the person's phone, with an email as the fallback.
- Individual review: decided in shaping at the ready gate. Automatic for a must-look reason (sensitive area, irreversible data, new dependency, security change); the person can also mark any piece.
- Error reporting and tracing tools for the later Live layers: decided when that extension is planned.
