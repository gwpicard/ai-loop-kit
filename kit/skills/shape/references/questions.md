# Questions

Ask in one batch of five questions at most. If you have more, keep the ones
that matter most for the build and write the rest under Notes as open
questions.

## The shape of a question

Each question has three parts:

- the question, in the person's words where you can;
- why it matters: what goes wrong in the build if the answer is missing;
- a recommended answer, labelled as yours, so the person can say yes in one word.

A question with no recommended answer is a sign that you have not read
enough. Read the code and the docs first. Never ask what a file can answer.

## What to ask first

1. The goal, if it is not clear.
2. The one flow the person will see, with a concrete example value.
3. The edge case that would hurt most, written as "When ..., then ...".
4. What must stay the same.

## Assumptions

A low-impact unknown does not need a question. Write it under Notes as an
assumption you made, so the person can review it. Silence is never an
answer to a real question. Ask again, shorter, with your recommended answer.

## Sensitive areas

When the idea touches money, personal data, sign-in or anything public, say
so once, plainly: what can go wrong. Offer a design that avoids the area if
there is one. Write the person's decision under Notes in their own words.
